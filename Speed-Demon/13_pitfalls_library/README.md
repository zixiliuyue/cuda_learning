### 🕳️ 坑 1：sync.Map 内存泄漏
**严重程度**：⭐⭐⭐⭐⭐  **踩坑人**：字节某电商团队  **时间**：2023年

**现象**：
服务跑了几天之后内存从 500MB 涨到了 8GB，OOM 重启，然后又慢慢涨。

**排查过程**：
1. heap profile 一看，80% 内存都是 `sync.Map` 的 entry 占的
2. key 明明已经删了，但 entry 还在
3. 查源码发现：`sync.Map.Delete()` 只是把 entry.p 设为 nil，打个标记，不会真删
4. 要等下次 dirty 升级成 read 的时候才会清理被删除的 key

**根因**：
我们的场景是 key 频繁增删，但是读很多，所以 dirty 永远不会升级，
删除的 key 永远占着内存，只增不减。

**解决方案**：
1. 改回 `RWMutex + map`，虽然锁竞争，但内存可控
2. 或者定期重建 sync.Map，把还在用的 key 移到新的里面去

**经验教训**：
> 不要只看特性，要读源码看边界条件！
> sync.Map 适合读多写少且 key 稳定的场景，
> 频繁增删 key 的场景绝对不要用！

**面试加分回答**：
> 我之前用 sync.Map 踩过内存泄漏的坑，原因是 Delete 只是打标记，不会立即释放内存，要等 dirty 升级才清理。读多写少但 key 频繁增减的场景不适合用 sync.Map。我们后来改成定期重建 map 或者换回 RWMutex+map 解决了。

### 🕳️ 坑 2：分片锁还是有竞争
**严重程度**：⭐⭐⭐⭐  **踩坑人**：阿里某广告团队  **时间**：2022年

**现象**：
为了解决全局锁竞争问题，把 map 拆成 32 分片，压测看锁竞争还是很严重。

**排查过程**：
1. mutex profile 一看，锁还是占了 40% CPU
2. 仔细看分片算法是按 key hash % 32，
3. 但热点 key 都哈希到同一个分片去了！

**根因**：
热点 key 分布不均匀，几个热点 key 都在同一个分片，
等于分片锁又退化成了全局锁。

**解决方案**：
1. 更均匀的哈希算法：换 fnv1a 或者 aes，不要用简单的求模
2. 热点 key 特殊处理，多复制几份，读的时候随机选一个副本
3. 极端情况可以用每个 Goroutine 本地缓存，异步同步

**优化结果**：
锁竞争从 40% 降到了 5% 以下。

**经验教训**：
> 分片锁不是银弹，还要看 key 分布是否均匀，
> 热点 key 问题是分布式系统的通用问题，
> 解决方向就是复制、打散、本地缓存。

### 🕳️ 坑 3：RWMutex 写饥饿
**严重程度**：⭐⭐⭐  **踩坑人**：腾讯某游戏团队  **时间**：2023年

**现象**：
读很多写很少，但写操作总是要等很久，P99 延迟特别高。

**排查过程**：
1. trace 看，写 Goroutine 老是拿不到锁，一直在等
2. 读操作源源不断，写操作优先级比读低
3. 只要读不断，写可能永远拿不到锁！

**根因**：
Go 的 RWMutex 是写公平模式，不是读优先也不是写优先：
- 有写者在等的时候，新的读者会被阻塞，排在写者后面
- 但是如果读者已经拿到锁了，写者要等所有读者释放
- 如果读特别多，写者要等很久很久

**解决方案**：
1. 控制并发读的数量，用信号量限制同时拿读锁的 Goroutine 数
2. 读写分离：多读几个副本，写操作写主副本，读操作读副本
3. 写少读多场景可以用 atomic.Value 替换 RWMutex

**经验教训**：
> 没有完美的锁，每种锁都有适用场景，
> 读超多写超少的场景，RWMutex 也会有问题，
> 压测的时候一定要测极端场景，比如 99.9% 读 0.1% 写。

### 🕳️ 坑 4：Mutex 拿了忘了放
**严重程度**：⭐⭐⭐⭐⭐  **踩坑人**：百度某搜索团队  **时间**：2022年

**现象**：
服务上线后跑了几小时突然卡住了，所有请求都超时，Goroutine 数疯涨。

**排查过程**：
1. goroutine profile 一看，几百个 Goroutine 都堵在拿同一个 Mutex
2. 看 stack trace，是某个日志库的全局锁
3. 追代码发现，有个 error path 忘记 defer Unlock 了
4. 一旦走到那个 error path，锁就永远被占住了，所有人都卡住

**根因**：
很简单，漏写了 defer mu.Unlock()

**解决方案**：
1. 加上 defer Unlock
2. 写个 Go 静态检查规则，所有 Lock() 之后必须紧跟着 defer Unlock()

**经验教训**：
> 这种错误很低级，但真的每个人都会犯。
> 最好的办法是代码规范 + 静态检查，不要相信人能记住。
> IDE 装个插件，拿了锁没放直接标红。

### 🕳️ 坑 5：Goroutine 泄漏 - 永远阻塞的发送者
**严重程度**：⭐⭐⭐⭐⭐  **踩坑人**：字节某短视频团队  **时间**：2023年

**现象**：
服务跑了几天之后 Goroutine 数涨到了 10 万+，内存也跟着涨，最后 OOM。

**排查过程**：
1. goroutine profile 一看，8 万个 Goroutine 都堵在同一行：`ch <- result`
2. 看代码逻辑：这是个异步写日志的 channel
3. 消费者那边处理不过来，channel 满了，发送者就永远阻塞在那了
4. 消费者为什么处理不过来？因为打日志的太多，消费速度跟不上生产速度

**根因**：
- channel 是无缓冲或者缓冲区太小
- 发送者没有超时或者丢弃机制，满了就永远堵在那

**解决方案**：
1. channel 加大缓冲，从 1000 改成 10 万
2. 发送者加 default 分支，满了就直接丢日志，不要阻塞业务
3. 加监控，channel 剩余空间少于 20% 就告警

```go
// ❌ 错误写法：满了就永远堵
ch <- log

// ✅ 正确写法：满了就丢，不阻塞业务
select {
case ch <- log:
default:
    // 日志满了，丢弃或者写到本地文件
    metric.Inc("log_drop_count")
}
```

**经验教训**：
> 所有 channel 发送操作都要考虑「满了怎么办」，
> 永远不要写没有 default 的阻塞发送，
> 非核心功能绝对不能阻塞核心业务。

### 🕳️ 坑 6：Context 忘 cancel，Goroutine 永远等
**严重程度**：⭐⭐⭐⭐  **踩坑人**：阿里某支付团队  **时间**：2023年

**现象**：
每次压测 Goroutine 数都会涨，压测结束也不下降，内存慢慢涨。

**排查过程**：
1. goroutine profile 看，一堆 Goroutine 堵在 `<-ctx.Done()`
2. 追代码，`ctx, cancel := context.WithTimeout(parent, 5*time.Second)`
3. 但是写完之后忘了调用 `cancel()`！
4. 所以这个 ctx 永远不会被取消，Goroutine 永远等在那

**根因**：
context.WithTimeout/WithCancel 创建的可取消 Context，
必须调用 cancel()，不然资源不会释放，Goroutine 泄漏。

**解决方案**：
1. 所有创建可取消 Context 的地方，必须紧跟着写 `defer cancel()`
2. 加静态检查规则，只要调用了 WithCancel 就必须调用 cancel

```go
// ❌ 错误写法：忘 cancel
ctx, _ := context.WithTimeout(parent, 5*time.Second)
result, err := http.Get(ctx, url)

// ✅ 正确写法
ctx, cancel := context.WithTimeout(parent, 5*time.Second)
defer cancel() // 这一行必须紧跟着写！
result, err := http.Get(ctx, url)
```

**经验教训**：
> 这坑 90% 的 Go 开发者都踩过，包括我。
> 现在 IDE 都会提醒黄色警告，但还是有人视而不见。
> 我的习惯是：敲完 WithCancel 下一行立刻敲 defer cancel()，
> 写完这两行再写后面的逻辑，形成肌肉记忆。

### 🕳️ 坑 7：for + select 没有退出分支
**严重程度**：⭐⭐⭐⭐  **踩坑人**：腾讯某社交团队  **时间**：2022年

**现象**：
服务重启后没事，跑个一两天 Goroutine 就涨几千，越来越慢。

**排查过程**：
1. goroutine profile 看，几千个 Goroutine 堵在 for + select 那一行
2. 看代码：

```go
// ❌ 坑货代码！
go func() {
    for {
        select {
        case e := <-eventChan:
            process(e)
        case <-time.After(1 * time.Minute):
            log.Info("no event for 1 minute")
        }
    }
}()
```

3. 问题是：eventChan 被关闭了之后，读关闭的 channel 会立即返回零值！
4. 所以 for 循环就永远空转！每秒循环几百万次！
5. 而且 time.After 每次循环都创建一个新的 Timer，也泄漏！

**解决方案**：
```go
// ✅ 正确写法
go func() {
    ticker := time.NewTicker(1 * time.Minute)
    defer ticker.Stop()

    for {
        select {
        case e, ok := <-eventChan:
            if !ok { // channel 关闭了，退出循环！
                return
            }
            process(e)
        case <-ticker.C:
            log.Info("no event for 1 minute")
        }
    }
}()
```

**经验教训**：
> for + select 是 Goroutine 泄漏的重灾区，
> 每个 for 循环都必须有明确的退出条件，
> 读 channel 一定要判断 ok，关闭了就退出！
> 还有 time.After 千万别在 for 里直接用，要用 Ticker。

### 🕳️ 坑 8：子 slice 引用大数组，GC 收不掉
**严重程度**：⭐⭐⭐⭐  **踩坑人**：百度某推荐团队  **时间**：2023年

**现象**：
服务处理每个请求都会加载一个 10MB 的特征向量，处理完只取前 100 个元素，
但内存占用一直很高，GC 也回收不掉。

**排查过程**：
1. heap profile 看，大部分内存都是 `[]float64` 占的
2. 代码逻辑：

```go
func loadFeatures() []float64 {
    // 加载 10MB 的特征向量
    features := make([]float64, 1024*1024)
    return features
}

func process() {
    features := loadFeatures()
    top100 := features[:100] // 只取前 100 个
    use(top100)
    // 以为 features 会被 GC 回收
}
```

3. 问题就在这：top100 只是个切片，底层引用的还是那整个 10MB 的大数组！
4. 只要 top100 还在引用，整个 10MB 就永远不会被 GC！

**解决方案**：
需要小切片的时候，copy 一份新的，不要引用原数组：

```go
func process() {
    features := loadFeatures()
    top100 := make([]float64, 100)
    copy(top100, features[:100]) // 复制一份，不引用原数组
    use(top100)
    // 现在 features 整个 10MB 可以被 GC 回收了
}
```

**经验教训**：
> Go 的 slice 只是个视图，不是拷贝！
> 从大 slice 切小 slice 的时候一定要想清楚，
> 大 slice 不需要了的话，小 slice 一定要 copy 一份新的，
> 不然整个大数组都被拖着，GC 收不掉。

### 🕳️ 坑 9：sync.Pool 放进去就被 GC 收了
**严重程度**：⭐⭐⭐  **踩坑人**：字节某直播团队  **时间**：2022年

**现象**：
用 sync.Pool 复用 buffer，但是 GC 之后 pool 就空了，性能没提升多少。

**排查过程**：
1. trace 看，每次 GC 之后 Pool 命中率直接跌到 0
2. 查源码才知道：sync.Pool 里的对象，每次 GC 都会被全部清掉！
3. 我们的业务刚好是每分钟一次高峰，高峰前 GC 了，Pool 就空了
4. 高峰来的时候又要重新分配对象，等于 Pool 白用了

**根因**：
Go 的 GC 每次都会把所有 Pool 里的对象清理掉，没有例外。
这是 Pool 的设计，不是 bug。

**解决方案**：
1. 自己在外面再套一层，比如用一个全局 slice 存一部分 hot 对象，GC 不会收
2. 或者 Pool 里放指针指向一个大结构，大结构里存很多小对象
3. 调大 GOGC，减少 GC 频率

**经验教训**：
> sync.Pool 是减少分配频率，不是消除分配，
> 不要指望 Pool 里的对象永远在，GC 说没就没，
> Pool 的命中率本来就不会是 100%，期望值管理好。

### 🕳️ 坑 10：小对象太多，GC 扫死
**严重程度**：⭐⭐⭐⭐⭐  **踩坑人**：阿里某电商团队  **时间**：2023年

**现象**：
服务 QPS 不高，只有 1 万，但 CPU 占了 70%，其中 50% 是 GC。

**排查过程**：
1. heap profile 看，每秒分配 100 多万个小对象，大部分是 16 字节、32 字节的
2. 追代码，都是打日志的时候创建的各种临时对象
3. fmt.Sprintf、各种 interface{} 转换，全在堆上分配

**解决方案**：
1. 所有 fmt.Sprintf 全换成复用的 strings.Builder
2. 日志库改成用 buffer 复用，每个 Goroutine 一个本地 buffer
3. 能不用 interface{} 就不用具体类型，避免逃逸
4. 关键路径打日志用静态字符串，不要动态拼接

**优化结果**：
- 每秒堆分配从 100 万降到 10 万
- GC CPU 占比从 50% 降到 8%
- P99 延迟从 200ms 降到 50ms

**经验教训**：
> Go 的 GC 虽然牛逼，但也架不住你疯狂分配小对象，
> 性能优化第一步永远是减少分配，
> 打日志这种看起来不重要的地方，往往是最大的分配来源。

### 🕳️ 坑 11：GOGC 调太大，OOM 了
**严重程度**：⭐⭐⭐⭐  **踩坑人**：腾讯某游戏团队  **时间**：2022年

**现象**：
为了减少 GC 频率，把 GOGC 从默认 100 调到了 500，
结果内存一涨就涨很多，有时候直接 OOM。

**排查过程**：
1. GOGC=500 的意思是：堆大小增长 5 倍才触发 GC
2. 本来默认 100 是用 1GB 触发 GC，现在要用到 5GB 才触发
3. 但是容器内存限制只有 4GB，还没等 GC 触发就先被 OOM kill 了

**解决方案**：
1. GOGC 不能瞎调，要根据容器内存限制来算
2. 比如容器限 4GB，可以设 GOGC=200 或者 300
3. 或者用 runtime/debug.SetGCPercent() 动态调整
4. 内存紧张的服务可以设 GOGC=50，GC 频繁点但安全

**经验教训**：
> GC 调优是权衡，不是越大越好越小越好。
> 要在 GC 频率、GC 停顿时间、内存占用三者之间找平衡点。
> 而且一定要用压测验证，不能拍脑袋改。

### 🕳️ 坑 12：Goroutine 太多，GC 扫描栈扫死
**严重程度**：⭐⭐⭐⭐  **踩坑人**：字节某订单团队  **时间**：2023年

**现象**：
服务有 10 万个 Goroutine，大部分都是 idle 状态，
每次 GC STW 时间都要 50ms 以上，P99 延迟很高。

**排查过程**：
1. trace 看，STW 大部分时间都花在扫描 Goroutine 栈
2. 10 万个 Goroutine，每个栈就算只有 2KB，也要扫 200MB
3. 而且 Goroutine 越多，扫描时间越久

**解决方案**：
1. 用 Worker Pool 控制 Goroutine 数量，不要每个请求一个 Goroutine
2. 从 10 万降到 1000，数量降了 100 倍
3. GC STW 时间从 50ms 降到了 2ms
4. P99 直接降了一半

**经验教训**：
> Goroutine 便宜但不是免费的，
> 上下文切换、栈内存、GC 扫描都是成本。
> 控制并发数是最基础的性能优化，
> 一般 CPU 核数 × 10 倍就足够了，再多反而变慢。

### 🕳️ 坑 13：MySQL IN 条件太多，慢到死
**严重程度**：⭐⭐⭐⭐  **踩坑人**：阿里某用户团队  **时间**：2022年

**现象**：
大促的时候某个接口突然超时，DB CPU 100%，
查询语句是 `SELECT * FROM users WHERE id IN (?,?,?,...)`，
IN 里面有 1000 多个 ID。

**排查过程**：
1. explain 一看，虽然走了索引，但扫描行数特别多
2. 原来 MySQL IN 条件太多的时候，会先把 IN 里的值排序，
3. 然后在索引树上做范围查找，1000 个值就要找 1000 次
4. 而且优化器会选错索引，有时候直接走全表扫描了

**解决方案**：
1. 限制 IN 条件的数量，最多 100 个，多了就分批查
2. 或者改成临时表 JOIN
3. 或者查出来之后应用层自己过滤

**优化结果**：
DB 查询时间从 2 秒降到了 10ms。

**经验教训**：
> 永远不要相信用户的输入，所有 IN 查询都要加长度限制，
> 不然有人传 1 万个 ID 进来，DB 直接就挂了。
> 而且这个问题平时测试不会发现，因为测试数据少，
> 只有线上大促的时候才爆。

### 🕳️ 坑 14：Redis Pipeline 忘 Exec，永远卡
**严重程度**：⭐⭐⭐  **踩坑人**：百度某搜索团队  **时间**：2023年

**现象**：
服务上线后慢慢变慢，Goroutine 越来越多，最后 OOM。

**排查过程**：
1. goroutine profile 看，几万个 Goroutine 都堵在 Redis 那一行
2. 看代码用了 Redis Pipeline，但是忘调用 Exec() 了！
3. 所以 Redis 连接永远被占着不会释放，新的请求永远等不到连接

**根因**：
go-redis Pipeline 必须调用 Exec() 才会真正发请求，释放连接，
如果只是 Get/Set 但是不 Exec，连接就永远被占住。

**解决方案**：
1. 加上 Exec()，而且必须 defer 处理错误
2. 加静态检查，Pipeline 创建之后必须调用 Exec

```go
// ❌ 错误写法
pipe := rdb.Pipeline()
pipe.Get(ctx, "key1")
pipe.Get(ctx, "key2")
// 忘 Exec 了！连接永远不释放！

// ✅ 正确写法
pipe := rdb.Pipeline()
pipe.Get(ctx, "key1")
pipe.Get(ctx, "key2")
_, err := pipe.Exec(ctx) // 必须调用！
if err != nil {
    // 处理错误
}
```

**经验教训**：
> 第三方库的坑防不胜防，
> 用新 API 之前一定要看文档，看 example，
> 不要想当然觉得它会自动执行。

## 🌐 网络/微服务相关坑

---

### 🕳️ 坑 15：HTTP 连接泄漏，端口用完
**严重程度**：⭐⭐⭐⭐  **踩坑人**：腾讯某社交团队  **时间**：2023年

**现象**：
服务跑了几天之后发现调下游接口越来越慢，最后直接报错 `cannot assign requested address`。

**排查过程**：
1. `netstat -anp | grep TIME_WAIT | wc -l` 一看，几万个 TIME_WAIT 连接
2. 端口都被占完了，没法新建连接
3. 看代码，每次请求都新建一个 http.Client，用完没关 Body！
4. 所以 TCP 连接永远不会被复用，也不会正常关闭，一直在 TIME_WAIT

**根因**：
http.Response.Body 必须 Close，不然连接泄漏。

**解决方案**：
```go
// ❌ 错误写法：忘关 Body
resp, err := http.Get(url)
if err != nil {
    return err
}
// 忘 resp.Body.Close()！连接泄漏！

// ✅ 正确写法：拿到 response 第一行就 defer Close
resp, err := http.Get(url)
if err != nil {
    return err
}
defer resp.Body.Close() // 这行必须紧跟着写！
```

**经验教训**：
> 所有需要关闭的资源，都要在拿到的第一行就写 defer Close，
> 不要等到后面再写，中间任何一个 return 就会泄漏。
> 这也是肌肉记忆，和 Context cancel 一样。

### 🕳️ 坑 16：熔断器设置太敏感，全熔断了
**严重程度**：⭐⭐⭐⭐  **踩坑人**：字节某推荐团队  **时间**：2022年

**现象**：
大促的时候某个下游接口偶尔超时，然后我们的熔断器直接熔断了，
导致所有请求都失败，整个推荐服务不可用。

**排查过程**：
1. 看熔断器配置：连续 5 次失败就熔断 30 秒
2. 大促的时候网络抖动，刚好连续 5 次超时
3. 然后就全熔断了，下游其实已经恢复了，但是我们 30 秒才半开探测

**解决方案**：
1. 调大阈值：连续 20 次失败才熔断
2. 调小熔断时间：5 秒就半开探测，不要 30 秒那么久
3. 加降级策略：熔断了可以返回旧数据或者默认值，不要直接报错

**经验教训**：
> 熔断器是保护下游的，不是给自己添堵的。
> 阈值要设置合理，不能太敏感，也不能太迟钝，
> 一定要有降级策略，熔断了之后服务还要能降级运行。
> 还有，定期混沌工程演练，故意把下游搞挂，看熔断是不是正常工作。

## 🔧 工具/方法论坑

---

### 🕳️ 坑 17：只看平均不看 P99，以为优化了其实没卵用
**严重程度**：⭐⭐⭐  **踩坑人**：所有团队都踩过  **时间**：年年有

**现象**：
优化完看平均延迟从 50ms 降到了 30ms，觉得很牛逼，
结果线上用户还是说卡，看 P99 反而从 200ms 涨到了 500ms。

**根因**：
- 平均延迟很容易被大量快的请求拉低
- 真正影响用户体验的是 P95、P99、P999
- 很多优化都是优化了 80% 的正常请求，
  但是让那 1% 的异常请求变得更慢了

**解决方案**：
1. 永远看 P99、P999，不要只看平均
2. 压测的时候一定要看延迟分布，不要只看 QPS
3. 优化前后 P99 没降，这个优化就不算成功

**经验教训**：
> 你永远不会杀死平均延迟，只会把它赶到 P99 去。
> 优化的时候眼睛一定要盯着长尾延迟，
> 99% 的用户体验是由 P99 决定的，不是平均值。

---

### 🕳️ 坑 18：profile 抓的时间不对，查了个寂寞
**严重程度**：⭐⭐⭐  **踩坑人**：所有人都踩过  **时间**：天天有

**现象**：
服务 CPU 高，抓了 10 秒 profile，一看都是 runtime 函数，
完全找不到业务代码的问题，查了半天啥也没查出来。

**排查过程**：
1. 后来才发现，抓 profile 的那 10 秒刚好服务在 GC，
2. 所以 profile 里全是 GC 相关的函数，
3. 根本看不到真正的热点代码在哪

**解决方案**：
1. profile 要抓多次，每次至少 30 秒
2. 抓的时候确认服务是不是在正常跑业务
3. 不要在重启后立刻抓，预热阶段不准
4. 要抓 peak 时间点的 profile，不要抓低峰期的

**经验教训**：
> profile 就像拍照片，要在问题发生的时候拍才有用，
> 问题都没发生的时候拍，当然什么都看不到。
> 最好在监控上配置自动抓 profile，CPU 超过阈值自动抓，
> 事后还能回溯。

## 🎯 总结：性能优化避坑指南

### 🔴 绝对不能犯的低级错误
1. Mutex 拿了忘放
2. Context 忘 cancel
3. HTTP Body 忘 Close
4. for + select 没有退出分支
5. channel 发送没有超时和丢弃策略

### 🟡 很容易踩的中级错误
1. 子 slice 引用大数组，GC 收不掉
2. sync.Map 频繁增删 key 内存泄漏
3. RWMutex 写饥饿
4. Goroutine 数量太多，GC 扫栈慢
5. GOGC 乱调导致 OOM

### 🟢 高级错误（踩过说明你真的干过）
1. 只看平均不看 P99
2. profile 抓的时间点不对，查了个寂寞
3. 分片锁但热点 key 还是集中
4. 熔断器太敏感反而搞出雪崩
5. 为了优化引入了更复杂的 bug

## 💡 面试的时候怎么说这些坑

面试的时候说坑，一定要按这个结构说，绝对加分：

```
1. 现象：当时发生了什么，有什么症状
2. 排查：我是怎么一步步查到根因的，用了什么工具
3. 根因：为什么会发生这个问题，本质原因是什么
4. 解决：我是怎么解决的，有哪几种方案，为什么选这个
5. 结果：优化前后的数据对比，具体数字
6. 反思：从这个坑里我学到了什么，以后怎么避免
```

**一定要有具体数字！**
不要说 "快了很多"，要说 "P99 从 200ms 降到了 50ms，GC 占比从 50% 降到了 8%"

**一定要说你踩过的坑！**
面试官面 10 个人，9 个只会背题，
只有你能清晰讲出你踩过什么坑怎么解决的，
你直接就脱颖而出了，SP offer 稳了！🚀
