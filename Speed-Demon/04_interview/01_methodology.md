# Go 性能调优方法论与排查流程

> 面试必问："说说你是怎么排查性能问题的？"

## 🎯 性能问题排查的通用方法论

### 第一步：定义问题（不要上来就瞎猜！）

**✅ 面试标准回答开头：**

> "我排查性能问题时，第一步是先搞清楚问题到底是什么。我会先收集四个方面的信息："

| 维度 | 需要回答的问题 | 收集方法 |
|-----|--------------|---------|
| **现象** | 具体怎么表现？慢？报错？超时？ | 用户反馈、监控、日志 |
| **范围** | 全环境？某些接口？特定时间段？ | 对比不同接口、不同时间 |
| **影响** | 影响多少用户？业务损失？ | 业务指标、SLA |
| **变化点** | 什么时候开始的？发版了？流量涨了？ | 发版记录、变更历史 |

**❌ 新手常犯错误**：上来就猜是 GC 问题、是锁竞争... 结果方向完全错了。

---

### 第二步：建立性能基线

**✅ 面试标准回答：**

> "然后我会建立一个性能基线，确保有可对比的数据。"

必须收集的基础指标：

| 层级 | 关键指标 | 获取方式 |
|-----|---------|---------|
| **应用层** | QPS、延迟（P50/P95/P99）、错误率 | Prometheus、日志 |
| **系统层** | CPU、内存、磁盘 IO、网络、Load | node_exporter、top、iostat |
| **Go 运行时** | Goroutine 数量、GC 次数、GC 停顿、堆大小 | pprof、runtime metrics |
| **依赖层** | DB 慢查、缓存命中率、下游服务延迟 | 中间件监控、链路追踪 |

**黄金法则**：没有基线，就没有优化。所有优化都要有前后对比。

---

### 第三步：假设驱动排查

**✅ 面试标准回答：**

> "接下来我会用假设驱动的方式排查：先假设可能的原因，再用数据验证，而不是盲目猜测。"

#### 常见假设树：

```
性能问题
  ├── CPU 高
  │   ├── 业务逻辑太复杂？ → pprof top 看热点
  │   ├── GC 太频繁？      → go gc trace + alloc profile
  │   ├── 死循环？         → trace 看 sysmon
  │   └── 序列化/反序列化？  → pprof 看 json 库
  ├── 内存高
  │   ├── 内存泄漏？        → heap profile + goroutine profile
  │   ├── 缓存太大？        → 看业务缓存实现
  │   └── 大对象未释放？    → heap profile inuse_space
  ├── 延迟高
  │   ├── 同步调用太多？     → 链路追踪看依赖
  │   ├── 锁竞争？          → mutex profile
  │   ├── 系统调用阻塞？    → trace 看 syscall
  │   └── 网络 I/O 慢？     → 抓包 + 服务端监控
  └── 吞吐量上不去
      ├── 并发度不够？       → 看 goroutine 数量
      ├── 连接池满了？       → DB/Redis 连接数
      └── 下游瓶颈？         → 看下游服务状态
```

---

### 第四步：定位瓶颈，逐个验证

**✅ 面试标准回答：**

> "然后我会用工具验证假设，找到真正的瓶颈。排查顺序是：先宏观，后微观；先全局，后局部。"

#### 工具使用优先级：

| 优先级 | 工具 | 能回答的问题 |
|-------|------|------------|
| **P0** | **监控大盘** | 问题是什么时候开始的？哪个指标异常？ |
| **P0** | **日志/链路追踪** | 慢请求都花在了哪里？ |
| **P1** | **execution trace** | 调度/GC/阻塞 都花了多久？ |
| **P1** | **pprof cpu** | CPU 都花在了哪里？ |
| **P2** | **pprof heap** | 内存都分配在了哪里？ |
| **P2** | **pprof mutex/block** | 锁竞争/阻塞严重吗？ |

**❌ 新手常犯错误**：上来就抓 cpu profile 看半小时，而不去先看一眼监控大盘。

---

### 第五步：实施优化 + 验证效果

**✅ 面试标准回答：**

> "定位瓶颈后，我会实施优化，然后用 benchmark 和压测来验证效果，确保优化有效。"

优化的三层考虑：

```
1. 架构层优化（收益最大）
   ├── 同步改异步
   ├── 加缓存
   ├── 批量操作
   ├── 减少依赖调用

2. 应用层优化
   ├── 算法优化
   ├── 减少内存分配
   ├── 并发优化
   ├── 锁粒度优化

3. 微优化（收益最小）
   ├── 循环优化
   ├── 内联
   ├── 内存对齐
```

**黄金法则**：先考虑架构优化，最后考虑微优化。不要上来就抠循环优化。

---

### 第六步：复盘 + 预防

**✅ 面试标准回答：**

> "最后我会复盘问题根因，加上监控和告警，避免同样的问题再次发生。"

必须做的事：
- 把问题写入团队故障手册
- 加上关键指标告警
- 完善压测用例，覆盖这个场景
- Code Review 时加入性能考量

## 🎯 真实排查流程演示

### 案例：线上接口 P99 延迟从 50ms 涨到 500ms

#### 第 1 分钟：看监控
- QPS 没变？排除流量原因
- CPU 涨了 3 倍？重点看 CPU
- GC 次数翻倍？可能和内存有关

#### 第 2 分钟：抓 profile
```bash
# 同时抓 cpu + heap + trace
curl http://localhost:6060/debug/pprof/profile?seconds=10
curl http://localhost:6060/debug/pprof/heap
curl http://localhost:6060/debug/pprof/trace?seconds=10
```

#### 第 5 分钟：分析
- `pprof top` → json.Marshal 占了 60% CPU
- `list json.Marshal` → 某接口返回了超大结构体
- `trace` → GC 标记 Assist 占了 30% 时间

#### 第 10 分钟：根因确认
- 最近发版加了个大结构体，每次都序列化
- 大量分配导致 GC 压力大
- GC 又加重了延迟

#### 第 15 分钟：修复
- 按需序列化，不需要的字段不要返回
- 预分配序列化 buffer
- 关键路径用 faster json 库

#### 第 30 分钟：验证 + 上线
- benchmark 确认延迟降回去了
- 上线 + 监控确认恢复

## 💯 面试加分项：怎么体现你懂性能优化？

### 回答模板 1：谈方法论
> "我觉得性能优化最重要的是方法论，而不是知道多少技巧。我的流程一般是：
> 1. 先通过监控和日志明确问题现象和范围
> 2. 建立性能基线，所有优化都要有数据对比
> 3. 用假设驱动排查，先猜可能的原因，再用工具验证
> 4. 找到瓶颈后按架构->应用->微优化的顺序考虑解决方案
> 5. 优化后一定要有压测验证效果
> 6. 最后复盘加监控，防止再犯"

### 回答模板 2：谈权衡
> "性能优化本质上是权衡。比如：
> - 用内存换 CPU（加缓存）还是用 CPU 换内存（流式处理）
> - 用空间换时间（预分配）还是用时间换空间
> - 用复杂度换性能（更复杂的算法）
> - 用一致性换性能（最终一致）
>
> 没有绝对的好，只有适合当前场景的选择。"

### 回答模板 3：谈可观测性
> "我觉得性能优化的前提是可观测性。如果没有好的监控、日志、链路追踪，性能问题根本没法查。
> 我们团队之前就是监控不完善，出了问题只能瞎猜，后来把四个黄金指标（延迟、流量、错误、饱和度）
> 都加上了，再出问题 5 分钟就能定位方向。"

## ⚠️ 性能优化常见误区（面试别踩坑！）

### ❌ 误区 1：过早优化
> "过早优化是万恶之源" - 但不做性能设计是更恶之源。
> **正确做法**：架构设计时考虑性能，编码时不要过度优化，出问题时再精准优化。

### ❌ 误区 2：只看平均延迟，不看 P99/P999
> 平均延迟很好，但 P99 爆炸。用户感知的是 P99，不是平均。
> **面试重点**：一定要提百分位指标，显得专业。

### ❌ 误区 3：优化了不存在的瓶颈
> 花了一周把某个函数从 1ms 优化到 0.1ms，但这个函数 QPS 只有 1。
> **正确做法**：先看热点占比，优先优化占比高的。

### ❌ 误区 4：只优化 QPS，不优化资源使用率
> QPS 上去了，但内存用了 10 倍。成本也是性能的一部分。
> **面试加分**：提到性能/成本 trade-off。

## 📋 性能问题排查清单（面试时可以一条条说）

- [ ] **1. 问题定义清楚了吗？** 慢的是哪个接口？慢了多少？影响范围？
- [ ] **2. 有变化点吗？** 最近发版了？流量涨了？配置改了？
- [ ] **3. 监控大盘看了吗？** CPU？内存？GC？错误率？
- [ ] **4. 是 CPU 瓶颈吗？** 使用率多少？用户态还是内核态？
- [ ] **5. 是内存瓶颈吗？** 一直在涨？GC 频率？
- [ ] **6. 是锁瓶颈吗？** mutex profile 看等待时间？
- [ ] **7. 是下游瓶颈吗？** DB？Redis？其他服务？
- [ ] **8. 有 goroutine 泄漏吗？** 数量一直在涨？
- [ ] **9. 优化前后有对比吗？** 基准测试？压测？
- [ ] **10. 监控告警加上了吗？** 下次能提前发现吗？

## 🎯 总结：性能工程师的核心能力

| 能力 | 说明 |
|-----|------|
| **问题定义** | 能把模糊的"慢"变成具体的指标和范围 |
| **工具使用** | 熟练使用 pprof、trace、链路追踪等 |
| **假设验证** | 能提出合理假设，并用数据证伪或证实 |
| **权衡思维** | 知道性能 vs 复杂度 vs 成本的权衡 |
| **数据驱动** | 所有决策都有数据支撑，不拍脑袋 |
| **系统思维** | 能从全链路角度看问题，不只盯着自己的代码 |

**记住**：面试时，比起你知道多少种优化技巧，面试官更看重你有没有系统的排查方法论。
