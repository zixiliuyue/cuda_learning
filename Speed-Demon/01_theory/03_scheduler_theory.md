# Go 调度器深度解析

## M:N 调度模型

### 三大核心实体

```
┌─────────────────────────────────────────────────────┐
│                    G (Goroutine)                    │
│  ┌───────────────────────────────────────────────┐  │
│  │  - 栈信息 (stack)                             │  │
│  │  - 程序计数器 (PC)                            │  │
│  │  - 状态: runnable, running, waiting           │  │
│  │  - 绑定的 M                                   │  │
│  └───────────────────────────────────────────────┘  │
└──────────────────────┬──────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│                    M (Machine)                      │
│  ┌───────────────────────────────────────────────┐  │
│  │  - 代表操作系统线程                            │  │
│  │  - 实际执行代码的实体                          │  │
│  │  - 绑定的 P                                   │  │
│  │  - 当前运行的 G                               │  │
│  └───────────────────────────────────────────────┘  │
└──────────────────────┬──────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────────────┐
│                    P (Processor)                    │
│  ┌───────────────────────────────────────────────┐  │
│  │  - 调度上下文                                  │  │
│  │  - 本地 runq (可运行的 G)                     │  │
│  │  - 内存缓存 (mcache)                          │  │
│  │  - 状态: idle, running, syscall               │  │
│  └───────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────┘
```

### 三者关系

```
          全局队列 (Global Run Queue)
                  │
         ┌────────┴────────┐
         │                 │
    ┌────▼───┐        ┌────▼───┐
    │   P0   │        │   P1   │  ... 更多 P
    │ runq   │        │ runq   │
    └───┬────┘        └───┬────┘
        │                  │
    ┌───▼───┐          ┌───▼───┐
    │   M0   │          │   M1   │  ... 更多 M
    └───┬───┘          └───┬───┘
        │                  │
    ┌───▼───┐          ┌───▼───┐
    │   G0   │          │   G1   │  ... 更多 G
    └────────┘          └────────┘
```

## 调度流程

### 正常调度

```
1. M 持有 P，从 runq 取 G
         │
         ▼
2. 执行 G 的代码
         │
         ▼
3. G 执行完成，保存状态
         │
         ▼
4. 回到 1，取下一个 G
```

### 调度时机

Goroutine 发生调度切换的时机：

1. **调用 runtime 函数** (如 go create, chan op, time.Sleep)
2. **系统调用前后**
3. **函数调用时可能发生栈扩张**
4. **垃圾回收 STW（Stop The World）时**

### Work Stealing 算法

当 P 的本地队列为空时：

```
当前 P 的 runq 为空
         │
         ▼
    尝试从全局队列取
         │
      成功? ──是──→ 执行
         │否
         ▼
    随机选一个 P
         │
         ▼
    偷取其一半 runq
         │
      成功? ──是──→ 执行
         │否
         ▼
    休眠等待
```

**为什么偷一半？**
- 平衡各 P 的负载
- 避免频繁的偷取操作
- 提高缓存命中率（同一个 P 上的 G 有更好的局部性）

## Goroutine 状态机

```
                      ┌───────────┐
       ┌─────────────▶│  Waiting  │◀────────────┐
       │              └─────┬─────┘             │
       │                    │ 阻塞解除           │
       │                    ▼                    │
  ┌────┴────┐          ┌───────────┐      ┌─────┴────┐
  │ Running │◀─────────│ Runnable  │──────▶ Syscall  │
  └────┬────┘          └───────────┘      └──────────┘
       │
       ▼
  ┌──────────┐
  │ Dead     │
  └──────────┘
```

### 状态转换说明

| 状态 | 说明 | 可能的转换 |
|-----|------|----------|
| Runnable | 等待执行，在 runq 中 | → Running |
| Running | 正在执行 | → Runnable, Waiting, Dead, Syscall |
| Waiting | 等待某个事件（channel, 锁等） | → Runnable |
| Syscall | 正在执行系统调用 | → Running |
| Dead | 执行完成，等待被清理 | - |

## 系统调用处理

### 阻塞系统调用

```
G 执行阻塞系统调用
         │
         ▼
M 陷入系统调用
         │
         ▼
P 与 M 解绑 (hand off)
         │
         ▼
P 寻找或创建新的 M'
         │
         ▼
新 M' 继续执行 P 上其他 G
         │
         ▼
系统调用返回
         │
         ▼
原 M 尝试获取空闲的 P
         │
         ▼
获取到 P → 继续执行 G
获取不到 → G 放入全局队列，M 休眠
```

### 为什么需要这么做？

**系统调用会阻塞 M，但这不应该阻塞 P 的调度**

- 没有这种机制，系统调用期间整个 P 都被阻塞
- 其他可运行的 G 无法执行
- 并发度会严重下降

## 调度器的公平性

### 抢占机制 (Preemption)

**Go 1.14+ 引入了基于信号的异步抢占**

```
    定时器中断 (SIGPROF)
             │
             ▼
    设置抢占标志
             │
             ▼
    在下一个安全点检查
             │
             ▼
    如果需要，让出 P
```

**安全点** = 不会导致数据结构不一致的位置，通常是：
- 函数调用入口
- 循环回边
- 栈检查时

### 抢占的触发条件

1. **G 运行超过 10ms** (抢占式调度)
2. **GC 需要 STW**
3. **显式调用 runtime.Gosched()**

### Go 1.14 之前的协作式抢占

```go
func (g *G) checkPreempt() {
    if g.stackguard0 = stackPreempt {
        morestack()  // 触发栈扩张，进而调度
    }
}
```

**问题**：无限循环且没有函数调用的 G 无法被抢占

## 调度器的性能调优

### GOMAXPROCS

**设置可并行执行的最大 P 数量**

```go
runtime.GOMAXPROCS(8)  // 设置为 8
```

**最佳实践**：
- 默认值 = CPU 核心数
- CPU 密集型应用: = 核心数
- I/O 密集型应用: 可以 > 核心数（但通常没必要）

**为什么？**
- 每个 P 需要一个物理核心才能真正并行
- 太多 P 会增加上下文切换开销

### 调度器追踪

使用 `GODEBUG=schedtrace=1000` 查看调度器状态：

```bash
GODEBUG=schedtrace=1000 ./yourapp
```

**输出解读**：
```
SCHED 0ms: gomaxprocs=8 idleprocs=8 threads=4 spinningthreads=0 idlethreads=0 runqueue=0 [0 0 0 0 0 0 0 0]
```

| 字段 | 含义 |
|-----|------|
| gomaxprocs | P 的数量 |
| idleprocs | 空闲 P 数量 |
| threads | 总 M 数量 |
| spinningthreads | 正在"自旋"找工作的 M |
| runqueue | 全局队列中的 G 数量 |
| [0 0 ...] | 每个 P 本地队列的 G 数量 |

### 调度延迟分析

使用 execution trace 可以看到：

```
G1 创建 → 排队等待 P0 → P0 可用 → 开始执行
                    ↑
               调度延迟
```

**常见调度延迟原因**：
1. 全局队列太长
2. Work stealing 不够高效
3. 太多 goroutine 同时就绪

## 常见调度模式问题

### 1. Goroutine 饥饿

**问题**：某些 G 长期得不到执行

**原因**：
- 长任务阻塞 P
- 优先级反转（Go 没有优先级，但实际可能发生）

**解决**：
- 长任务主动调用 runtime.Gosched()
- 使用带缓冲的 channel 控制并发

### 2. 惊群效应 (Thundering Herd)

**问题**：
```go
ch := make(chan struct{})
for i := 0; i < 1000; i++ {
    go func() {
        <-ch  // 1000 个 goroutine 等待
    }()
}
close(ch)  // 突然唤醒全部！
```

**后果**：
- 所有 G 同时被唤醒
- 竞争 P，造成调度风暴
- 大量上下文切换开销

### 3. 自旋过多

**问题**：太多 M 在自旋等待工作

**表现**：
- spinningthreads 数值高
- CPU 使用率高但实际工作少

**解决**：
- 调整 goroutine 创建模式
- 使用 worker pool 模式

## 并发模式的调度考量

### Worker Pool

```
                    ┌──────────┐
              ┌────▶│ Worker 1 │
              │     └──────────┘
  任务队列 ───┤        ...
              │     ┌──────────┐
              └────▶│ Worker N │
                    └──────────┘
```

**调度优势**：
- 固定数量的 goroutine，调度压力小
- 任务队列天然均衡各 worker
- 更好的缓存局部性

### Fan-out/Fan-in

```
      ┌─────┐
      │  G1 │──┐
      └─────┘  │
┌──────┐  │    │   ┌────────┐
│  G0  │──┼───▶│──▶│  Gout  │
└──────┘  │    │   └────────┘
      ┌─────┐  │
      │  G2 │──┘
      └─────┘
```

**潜在问题**：
- 太多 G 同时创建
- 调度器压力大
- 内存开销高

## 调度器演进

### Go 1.0
- 简单的 M:N 调度
- 没有 work stealing
- 全局锁竞争严重

### Go 1.1
- 引入 work stealing
- 性能大幅提升

### Go 1.5
- GC 改进
- 调度器微调

### Go 1.14
- 异步抢占
- 彻底解决无限循环阻塞问题

### 未来
- 可能引入优先级调度
- 更好的 NUMA 感知
- 更高效的 I/O 集成
