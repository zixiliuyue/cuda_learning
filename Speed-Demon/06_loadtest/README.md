## 🛠️ 常用压测工具对比

| 工具 | 适用场景 | 优点 | 缺点 |
|-----|---------|-----|
| **hey** | HTTP 压测 | Go 写的，输出友好，简单 | 功能简单 |
| **wrk** | 高性能 HTTP 压测 | C 写的，性能之王 | Lua 脚本学习曲线 |
| **ab** | 简单 HTTP 压测 | 系统自带 | 老，功能少 |
| **k6** | 复杂场景压测 | JS 脚本化，可观测好 | 性能稍重 |
| **JMeter** | 全场景 | 功能最全 | 重，Java |

## 🚀 hey 快速上手（最常用）

### 安装
```bash
# Mac
brew install hey

# Linux
wget https://hey-linux-amd64.deb && dpkg -i hey-linux-amd64.deb

# Go 源码
go install github.com/rakyll/hey@latest
```

### 基础用法

```bash
# 100 并发，总共 3000 请求
hey -n 3000 -c 100 http://localhost:8080/api
```

### 完整参数
```bash
hey [选项
-n 3000           # 总请求数
-c 100              # 并发数
-z 30s              # 压测时间，和 -n 二选一
-t 30               # 请求超时，默认 20 秒
-H "Auth: Bearer xxx"  # Header
-m POST             # 请求方法
-d '{"id":123}'  # POST Body
-T application/json
-o csv             # 输出格式
-disable-keep-alive false   # 不 KeepAlive
-disable-compression false
```

## 🎯 正确的压测流程

### Step 1: 先跑基准线
```bash
# 从低并发，先看系统稳定状态
hey -n 1000 -c 10 http://...
```
看：QPS 是多少？P99 是多少？CPU/内存？

### Step 2: 逐步加并发
```bash
# 每次加倍
hey -n 2000 -c 20 http://...
hey -n 4000 -c 40 http://...
hey -n 8000 -c 80 http://...
hey -n 16000 -c 160 http://...
```
每轮间隔 30 秒让系统缓一缓

### Step 3: 找拐点
什么时候 QPS 不再涨，延迟开始暴涨？那就是系统极限！

### Step 4: 压测同时抓 profile
```bash
# 开 3 个终端
1. 终端 1: 压测
hey -n 10000 -c 100 http://...

2. 终端 2: 压测中间抓 profile
go tool pprof http://.../profile?seconds=10

3. 终端 3: 观察指标
while true; do curl http://.../stats; sleep 1; done
```

## ⚠️ 压测的 8 个坑

### ❌ 坑 1: 压测客户端和服务端在同一台机器！
**现象**：CPU 抢资源互抢，结果不准！
**解决**：分开两台机器压！

### ❌ 坑 2: 长连接 vs 短连接
```bash
# 默认是 KeepAlive（复用连接）
hey ...

# 要测短连接（每次新建连接
hey -disable-keepalive ...
```
**面试问：你们线上是长连接还是短连接？压测要对齐！

### ❌ 坑 3: 只有一个接口参数！
**现象**：所有请求都走缓存热点！
**解决**：准备 URL 列表文件，随机选，避免热点

### ❌ 坑 4: 压测时间太短
**现象**：压 5 秒，GC 还没触发！
**解决**：至少压 30 秒以上，最好 1-5 分钟

### ❌ 坑 5: 忽略错误率
**现象**：QPS 很高，但 50% 都是 500 错误！
**解决**：看 200 响应码数量！

### ❌ 坑 6: 压测客户端本身压测客户端瓶颈！
**现象**：客户端 CPU 100%，但服务端只用了 30%！
**解决**：看客户端机器配置！

### ❌ 坑 7: 不预热
**现象**：前几秒 JIT/GC 没热身！
**解决**：先跑 1000 次预热

### ❌ 坑 8: 只看平均不看 P99
**现象**：平均 50ms 很好，但 P99 2 秒！
**解决**：P50/P90/P95/P99 都要看！

## 📊 怎么判断压测要记录哪些指标

### 客户端指标（hey 输出）：
- ✅ QPS（Requests/sec）
- ✅ P50/P90/P95/P99 延迟
- ✅ 成功率（200 OK 数量
- ✅ 最慢的 10 个请求

### 服务端指标：
- ✅ CPU 使用率
- ✅ 内存（GC 次数/GC 停顿
- ✅ Goroutine 数量
- ✅ 线程数
- ✅ 网络 IO

### 下游指标：
- ✅ DB CPU/连接数/慢查
- ✅ Redis 命中率/QPS
- ✅ 其他下游服务延迟

## 💯 面试回答模板

> **面试官问："怎么给一个接口做性能压测？"

> **你回答：**

> "我一般按这几步做：
>
> **第一步：定目标是什么？
> 先明确压测目标：比如接口 P99 要在 200ms 以内，QPS 1000。
>
> **第二步：准备压测环境**
> - 和线上配置尽量一样，数据量也要对齐，不能线上量级，比如 DB 数据量要够。
> 然后客户端和服务端要在不同机器避免互相影响。
>
> **第三步：先跑基准线
> 先低并发跑 10 并发先跑一轮，看系统稳定后的基础 QPS 和延迟，记录下来作为基线。
>
> **第四步：逐步加并发
> 从 10 → 20 → 50 → 100 → 200，每次加完等系统稳定后再下一轮，
> 中间一直加到 QPS 不再涨，延迟开始暴涨就是系统瓶颈了。
>
> **第五步：压测过程中同时抓 profile
> CPU profile、heap、trace 都抓，还要看监控，四个黄金指标都观察。
>
> **第六步：分析瓶颈
> 比如 CPU 高不高？锁不高不高？下游慢不慢？数据库？
>
> **第七步：优化后再对比
> 优化后再跑同样的对比，确认优化效果确实有效。
>
> **第八步：注意几个坑要注意：
> 要预热、要注意区分长短连接对齐线上情况、参数不要只看平均延迟、错误率、客户端本身会不会有瓶颈。
> 最重要的是：不是为了压测是为了找瓶颈，不是为了好看！

## 🎯 进阶：wrk 脚本化压测

### 安装 wrk：
```bash
brew install wrk
```

### 基础用法：
```bash
# 8 线程，200 并发，压 30 秒
wrk -t8 -c200 -d30s http://...
```

### 用 Lua 脚本造复杂请求：
```lua
-- script.lua
request = function()
    local path = "/api/user?id=" .. math.random(1, 10000)
    return wrk.format(nil, path, nil)
end
```

运行：
```bash
wrk -t8 -c200 -d30s -s script.lua http://...
```
