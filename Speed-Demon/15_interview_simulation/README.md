### 问题1：CUDA内存层次结构

#### 面试官追问层级
- **L1**：请描述CUDA的内存层次结构
- **L2**：各种内存的特点和适用场景是什么？
- **L3**：在实际项目中，你是如何选择使用哪种内存的？

#### 评分标准（0-5分）
| 分数 | 打分点说明 |
|------|-----------|
| 0分 | 完全不了解CUDA内存模型 |
| 1分 | 只知道global memory，不知道其他内存类型 |
| 2分 | 能说出3种以上内存类型，但不清楚各自特点 |
| 3分 | 能完整描述内存层次结构，知道各种内存的速度和容量 |
| 4分 | 能结合具体场景说明每种内存的适用场景 |
| 5分 | 能分析不同内存选择对性能的影响，并给出优化策略 |

#### 满分回答示例
> CUDA的内存层次结构从快到慢、容量从小到大依次是：
> 
> 1. **寄存器（Register）**：每个线程私有，速度最快（~1个时钟周期），容量最小（每个SM约64KB-256KB）。用于存储线程的局部变量。
> 
> 2. **共享内存（Shared Memory）**：每个线程块共享，速度很快（~1-2个时钟周期），容量约48KB-168KB/SM。用于线程块内的数据共享和数据复用。
> 
> 3. **L1缓存**：可选配置为16KB/32KB/48KB，与共享内存共用硬件资源。缓存global memory访问。
> 
> 4. **L2缓存**：所有SM共享，容量约1.5MB-40MB，统一缓存所有SM的global memory访问。
> 
> 5. **全局内存（Global Memory）**：所有线程都可访问，容量最大（GB级），但速度最慢（~300-500个时钟周期）。用于存储主要数据。
> 
> 6. **常量内存（Constant Memory）**：只读，容量64KB，有专门的缓存。用于存储只读的常量数据。
> 
> 7. **纹理内存（Texture Memory）**：只读，针对2D空间局部性优化。用于图像和纹理数据。
> 
> **选择策略**：
> - 需要频繁访问的线程私有数据 → 寄存器
> - 线程块内需要共享的数据 → 共享内存
> - 只读且所有线程访问相同地址的数据 → 常量内存
> - 有2D空间局部性的图像数据 → 纹理内存
> - 大量数据存储 → 全局内存，但要注意合并访问
> 
> 在实际项目中，我会先用nvvp分析内存访问模式，然后根据数据访问频率和访问模式选择最合适的内存类型。

#### 反面教材示例
> CUDA有global memory和shared memory，global memory比较大，shared memory比较快。一般就用global memory存数据，需要快一点就用shared memory。

### 问题2：线程束分化（Warp Divergence）

#### 面试官追问层级
- **L1**：什么是线程束分化？
- **L2**：线程束分化是如何影响性能的？
- **L3**：如何避免或减少线程束分化？

#### 评分标准（0-5分）
| 分数 | 打分点说明 |
|------|-----------|
| 0分 | 不知道线程束分化是什么 |
| 1分 | 只听说过这个概念，说不清楚原理 |
| 2分 | 能描述线程束分化的现象 |
| 3分 | 能解释线程束分化的性能影响机制 |
| 4分 | 能说出2种以上避免线程束分化的方法 |
| 5分 | 能结合具体代码案例说明如何优化线程束分化 |

#### 满分回答示例
> **什么是线程束分化**：
> CUDA以32个线程为一个线程束（Warp）执行。当同一个Warp内的线程遇到条件分支时，不同线程可能走向不同的分支路径，这就是线程束分化。
> 
> **性能影响**：
> - GPU硬件会串行执行不同的分支路径
> - 比如一个Warp中有一半线程走if分支，一半走else分支，那么总执行时间是两个分支时间之和
> - 理论上最坏情况性能下降32倍
> 
> **如何避免**：
> 
> 1. **分支条件按Warp对齐**：让同一个Warp内的线程走相同分支
> ```cuda
> // 优化前：可能分化
> if (threadIdx.x % 2 == 0) { ... }
> 
> // 优化后：按Warp对齐
> if (threadIdx.x / 32 % 2 == 0) { ... }
> ```
> 
> 2. **使用分支谓词（Branch Predication）**：对于短小的分支，编译器可能自动谓词化
> 
> 3. **重构代码逻辑**：将条件判断转换为计算
> ```cuda
> // 优化前
> if (x > 0) { y = a; } else { y = b; }
> 
> // 优化后：使用选择指令
> y = x > 0 ? a : b;
> ```
> 
> 4. **数据重排**：让相邻线程处理相邻数据，减少分支分歧
> 
> 5. **使用模板和编译期常量**：让分支在编译期确定
> 
> 我在实际项目中遇到过一个图像处理的Kernel，因为每个像素的阈值判断不同导致严重的Warp分化。通过将阈值判断向量化，并使用共享内存预取数据，最终性能提升了2.3倍。

#### 反面教材示例
> 线程束分化就是线程执行不同的代码，对性能有影响。优化的话就是尽量少用if-else语句。

### 问题3：全局内存合并访问

#### 面试官追问层级
- **L1**：什么是全局内存合并访问？
- **L2**：不同架构（Fermi、Kepler、Ampere）的合并访问规则有什么差异？
- **L3**：如果无法实现合并访问，有什么优化策略？

#### 评分标准（0-5分）
| 分数 | 打分点说明 |
|------|-----------|
| 0分 | 完全不知道合并访问概念 |
| 1分 | 听说过合并访问，知道对性能重要 |
| 2分 | 能描述合并访问的基本要求 |
| 3分 | 能说明不同架构的合并访问机制差异 |
| 4分 | 能分析不合并访问的性能损失 |
| 5分 | 能给出多种不合并访问场景下的优化策略 |

#### 满分回答示例
> **什么是合并访问**：
> 当一个Warp内的所有线程访问全局内存时，如果它们的内存地址是连续的且对齐的，GPU可以将这些访问合并成一个或几个内存事务，这就是合并访问。
> 
> **不同架构的差异**：
> 
> 1. **Fermi及更早（计算能力2.x）**：
>    - 严格对齐要求：必须对齐到128字节边界
>    - 线程顺序必须严格递增
>    - 不满足则完全不合并，分成32次独立访问
> 
> 2. **Kepler-Maxwell（3.x-5.x）**：
>    - 放宽对齐要求
>    - 支持散列收集（Gather）
>    - 地址分散但在同一个128字节缓存行内也能合并
> 
> 3. **Pascal-Ampere（6.x-8.x）**：
>    - 支持缓存行内任意地址合并
>    - 支持更多的合并模式
>    - 引入L2缓存压缩，进一步提高效率
> 
> **不合并访问的优化策略**：
> 
> 1. **使用共享内存转置**：
> ```cuda
> __shared__ float smem[32][32];
> // 合并读入共享内存
> smem[threadIdx.y][threadIdx.x] = global[...];
> __syncthreads();
> // 从共享内存随机访问
> float val = smem[threadIdx.x][threadIdx.y];
> ```
> 
> 2. **数据重排（SoA vs AoS）**：
> ```cuda
> // 优化前：AoS，不合并
> struct Point { float x, y, z; };
> 
> // 优化后：SoA，合并访问
> struct Points { float* x, *y, *z; };
> ```
> 
> 3. **使用向量加载指令**：float2, float4等
> ```cuda
> float4 data = *reinterpret_cast<float4*>(global + idx * 4);
> ```
> 
> 4. **调整线程映射方式**：让相邻线程访问相邻地址
> 
> 在Ampere架构上，虽然合并要求放宽了，但良好的合并访问仍能带来2-4倍的性能提升。我曾经优化过一个矩阵转置Kernel，通过共享内存转置实现完全合并访问，性能提升了5倍。

#### 反面教材示例
> 合并访问就是线程连续访问内存，这样比较快。如果不合并的话，程序就会变慢。

### 问题4：共享内存Bank冲突

#### 面试官追问层级
- **L1**：什么是共享内存Bank冲突？
- **L2**：Bank冲突是如何产生的？
- **L3**：如何避免Bank冲突？

#### 评分标准（0-5分）
| 分数 | 打分点说明 |
|------|-----------|
| 0分 | 完全不知道Bank冲突 |
| 1分 | 听说过这个概念 |
| 2分 | 能描述Bank冲突的现象 |
| 3分 | 能解释Bank冲突的产生机制 |
| 4分 | 能说出几种避免Bank冲突的方法 |
| 5分 | 能设计不同的数据布局来消除Bank冲突 |

#### 满分回答示例
> **什么是Bank冲突**：
> 共享内存被分成32个（或64个，依架构而定）相等大小的Bank，每个Bank可以独立访问。如果同一个Warp内的多个线程访问同一个Bank的不同地址，就会产生Bank冲突，导致访问串行化。
> 
> **产生机制**：
> - 每个Bank宽度通常是4字节（32位）或8字节（64位）
> - 地址映射：Bank Index = Address / SizeOfBank % NumberOfBanks
> - 冲突度：n个线程访问同一个Bank → 冲突度n → 需要n次访问才能完成
> 
> **常见的冲突模式**：
> 1. **跨步访问（步长为32的倍数）**：严重冲突
> 2. **行列访问转置**：常见于矩阵操作
> 3. **广播访问**：同一个地址，不算冲突，是广播
> 
> **避免策略**：
> 
> 1. **填充（Padding）**：增加一列，改变步长
> ```cuda
> // 优化前：32x32，步长32 → 冲突
> __shared__ float smem[32][32];
> 
> // 优化后：32x33，步长33 → 无冲突
> __shared__ float smem[32][33];
> ```
> 
> 2. **改变访问顺序**：
> ```cuda
> // 优化前：冲突
> val = smem[threadIdx.x][threadIdx.y];
> 
> // 优化后：调整索引
> val = smem[threadIdx.y][threadIdx.x];
> ```
> 
> 3. **使用向量类型**：float2, float4等，每个线程访问多个连续Bank
> 
> 4. **循环展开 + 重排访问顺序**：
> ```cuda
> #pragma unroll
> for (int i = 0; i < 32; i++) {
>     val += smem[(threadIdx.x + i) % 32][threadIdx.y];
> }
> ```
> 
> 5. **利用广播机制**：所有线程读同一个地址时是广播，不是冲突
> 
> Bank冲突的最坏情况会导致共享内存访问性能下降32倍。我在优化一个FFT Kernel时，通过合理的共享内存填充和访问顺序调整，消除了所有Bank冲突，Kernel整体性能提升了2.8倍。

#### 反面教材示例
> Bank冲突就是多个线程访问同一个内存块，会变慢。优化的话就是让它们访问不同的Bank。

### 问题5：CUDA流（Stream）与重叠执行

#### 面试官追问层级
- **L1**：什么是CUDA流？
- **L2**：如何利用CUDA流实现计算与数据传输重叠？
- **L3**：在多GPU场景下如何高效使用流？

#### 评分标准（0-5分）
| 分数 | 打分点说明 |
|------|-----------|
| 0分 | 完全不知道CUDA流 |
| 1分 | 听说过CUDA流但没用过 |
| 2分 | 知道流的基本概念和创建方法 |
| 3分 | 能说明流的异步执行和重叠机制 |
| 4分 | 能设计计算与数据传输重叠的流水线 |
| 5分 | 能在复杂场景（多GPU、多任务）下流的最佳实践 |

#### 满分回答示例
> **什么是CUDA流**：
> CUDA流是一系列按顺序执行的GPU操作（Kernel执行、数据传输等）。不同流之间的操作可以并行执行，同一流内的操作按提交顺序执行。
> 
> **重叠执行的条件**：
> GPU有多个独立引擎：
> - 计算引擎（多个SM）
> - 数据传输引擎（DMA，通常有2个：HtoD和DtoH）
> 
> 这些引擎可以并行工作，实现：
> - Kernel计算与数据传输重叠
> - 不同流的Kernel之间并行执行
> - HtoD和DtoH同时进行
> 
> **实现计算与传输重叠**：
> 
> 1. **分页锁定内存（Pinned Memory）**：
> ```cuda
> cudaMallocHost(&host_ptr, size);  // 必须用pinned内存
> ```
> 
> 2. **创建多个流**：
> ```cuda
> cudaStream_t streams[N_STREAMS];
> for (int i = 0; i < N_STREAMS; i++) {
>     cudaStreamCreate(&streams[i]);
> }
> ```
> 
> 3. **流水线设计**：
> ```cuda
> for (int i = 0; i < N_STREAMS; i++) {
>     // 第i个流：HtoD传输
>     cudaMemcpyAsync(dev_ptr[i], host_ptr[i], size, 
>                      cudaMemcpyHostToDevice, streams[i]);
>     
>     // 第i个流：Kernel执行
>     myKernel<<<grid, block, 0, streams[i]>>>(dev_ptr[i]);
>     
>     // 第i个流：DtoH传输
>     cudaMemcpyAsync(host_ptr[i], dev_ptr[i], size, 
>                      cudaMemcpyDeviceToHost, streams[i]);
> }
> ```
> 
> **多GPU场景的流使用**：
> 
> 1. **每个GPU独立的流池**：避免GPU之间的流干扰
> 
> 2. **使用cudaStreamCreateWithPriority**：给关键任务更高优先级
> 
> 3. **流同步策略**：
>    - cudaStreamSynchronize(stream)：等待特定流完成
>    - cudaEventSynchronize(event)：使用事件更灵活
>    - cudaStreamWaitEvent(stream, event)：流间依赖
> 
> 4. **注意事项**：
>    - 流不是越多越好，一般2-4个流就能获得较好的重叠
>    - 过多流会增加调度开销
>    - 合理划分数据块大小，平衡传输和计算时间
> 
> 我在一个视频处理项目中，使用4个流实现了计算与传输的完全重叠，端到端性能提升了2.7倍。nvvp分析显示GPU利用率从35%提升到95%。

#### 反面教材示例
> CUDA流就是让程序异步执行，可以让多个Kernel同时跑。创建几个流，然后把Kernel放到不同流里就行了。

### 问题6：动态并行（Dynamic Parallelism）

#### 面试官追问层级
- **L1**：什么是动态并行？
- **L2**：动态并行的适用场景是什么？
- **L3**：动态并行有什么性能开销？如何优化？

#### 评分标准（0-5分）
| 分数 | 打分点说明 |
|------|-----------|
| 0分 | 完全不知道动态并行 |
| 1分 | 听说过动态并行 |
| 2分 | 知道动态并行是在GPU上启动Kernel |
| 3分 | 能说明动态并行的适用场景 |
| 4分 | 能分析动态并行的性能开销 |
| 5分 | 能给出动态并行的优化策略 |

#### 满分回答示例
> **什么是动态并行**：
> 动态并行允许GPU线程直接在设备上启动新的Kernel，而不需要CPU参与。这使得递归算法和分治策略可以在GPU上自然实现。
> 
> **适用场景**：
> 
> 1. **递归算法**：
>    - 快速排序、归并排序
>    - 树遍历（KD树、BVH）
>    - 分治算法
> 
> 2. **自适应计算**：
>    - 计算复杂度取决于数据的算法
>    - 网格自适应细化
>    - 光线追踪中的递归反弹
> 
> 3. **层次化问题**：
>    - 多级网格求解器
>    - 多尺度模拟
> 
> **性能开销**：
> 
> 1. **启动开销**：子Kernel启动比CPU启动慢，约5-10µs
> 2. **内存开销**：需要额外的设备端运行时支持
> 3. **调度开销**：父子网格之间的同步
> 4. **资源限制**：设备端Kernel launch有深度限制（通常24层）
> 
> **优化策略**：
> 
> 1. **粒度过滤**：小任务不启动子Kernel，直接在父线程中执行
> ```cuda
> __global__ void parent_kernel(...) {
>     if (problem_size < THRESHOLD) {
>         // 小任务直接计算，不启动子Kernel
>         compute_directly(...);
>     } else {
>         child_kernel<<<grid, block>>>(...);
>     }
> }
> ```
> 
> 2. **批量启动**：合并多个小子Kernel为一个大Kernel
> 
> 3. **使用设备端队列**：减少启动开销
> 
> 4. **合理设置粒度阈值**：
>    - 太小：启动开销大
>    - 太大：并行度不足
>    - 通常几千个线程的工作量比较合适
> 
> 5. **避免深度递归**：递归深度不要超过设备限制
> 
> 6. **使用cudaDeviceSynchronize() vs 事件同步**：
>    - 父Kernel中等待子Kernel用cudaDeviceSynchronize()
>    - 也可以用事件实现更细粒度的同步
> 
> 我在实现GPU上的BVH构建时使用了动态并行。通过设置合适的粒度阈值（叶子节点数<128时不启动子Kernel），动态并行版本比纯CPU实现快15倍，比传统的迭代式GPU实现快2.3倍。

#### 反面教材示例
> 动态并行就是在GPU上启动Kernel，这样就不用CPU控制了。适合递归的算法，比如快速排序什么的。

### 问题7：性能分析与优化方法论

#### 面试官追问层级
- **L1**：你常用哪些CUDA性能分析工具？
- **L2**：性能优化的一般流程是什么？
- **L3**：如何定位性能瓶颈？

#### 评分标准（0-5分）
| 分数 | 打分点说明 |
|------|-----------|
| 0分 | 没用过任何性能分析工具 |
| 1分 | 只知道nvprof |
| 2分 | 能使用nvprof进行基本分析 |
| 3分 | 有完整的性能优化方法论 |
| 4分 | 能结合工具定位具体瓶颈 |
| 5分 | 能系统性地分析和优化复杂应用 |

#### 满分回答示例
> **常用工具**：
> 
> 1. **NVIDIA Visual Profiler (nvvp)**：可视化分析，查看时间线、内存、分支分化等
> 2. **nvprof**：命令行分析，适合自动化和脚本
> 3. **Nsight Systems**：系统级分析，CPU/GPU交互，API调用
> 4. **Nsight Compute**：Kernel级细粒度分析，指令级统计
> 5. **CUDA Samples中的metrics**：通过CUDA API获取性能计数器
> 
> **性能优化方法论（五步法）**：
> 
> **Step 1：测量与基线建立**
> ```bash
> # 总体性能
> nvprof ./application
> 
> # 详细指标
> nvprof --metrics achieved_occupancy,branch_efficiency,gld_efficiency ./app
> ```
> 
> **Step 2：定位瓶颈**
> 使用自上而下的方法：
> - 先看端到端时间：是CPU还是GPU瓶颈？
> - 如果是GPU瓶颈：是计算瓶颈还是内存瓶颈？
> - 看关键指标：
>   - 计算瓶颈：算术强度高，SM利用率高
>   - 内存瓶颈：gld_efficiency低，内存带宽接近上限
>   - 延迟隐藏：achieved_occupancy低
> 
> **Step 3：分析根本原因**
> | 现象 | 可能原因 |
> |------|---------|
> | SM利用率低 | Grid/Block配置不当，Kernel太小 |
> | 内存效率低 | 合并访问差，Bank冲突 |
> | 分支效率低 | Warp分化严重 |
> | 指令吞吐量低 | 指令依赖链过长 |
> 
> **Step 4：实施优化**
> 每次只优化一个方面，测量效果：
> 1. 内存优化（合并访问、共享内存）
> 2. 指令级优化（Warp分化、指令选择）
> 3. 并行度优化（Occupancy、流）
> 4. 算法级优化
> 
> **Step 5：验证与迭代**
> - 正确性验证：优化不改变结果
> - 性能验证：优化确实带来提升
> - 回归测试：不引入新问题
> 
> **定位瓶颈的实战技巧**：
> 
> 1. ** roofline模型分析**：
>    - 计算算术强度 = 浮点操作数 / 字节访问数
>    - 与roofline比较，确定是计算还是内存 bound
> 
> 2. **限制因子分析**：
>    - 逐渐增加问题规模，看哪个资源先达到极限
>    - 寄存器、共享内存、线程数
> 
> 3. **二分法定位**：
>    - 注释掉部分代码，看性能变化
>    - 快速定位问题代码段
> 
> 我最近优化的一个推荐系统推理Kernel，首先用nvprof发现achieved_occupancy只有25%，然后用Nsight Compute看到是寄存器使用过多导致。调整编译选项使用--use_fast_math和--maxrregcount=64，Occupancy提升到75%，性能提升了2.1倍。

#### 反面教材示例
> 性能优化就是用nvvp看看哪里慢，然后改改代码。主要就是用共享内存，减少全局内存访问。

> 
> **优化过程**：
> 
> **阶段1：性能分析（1周）**
> - 使用nvvp分析发现三个主要瓶颈：
>   1. 多个Kernel之间的频繁同步和数据传输（占35%时间）
>   2. 卷积操作的内存访问效率低（占40%时间）
>   3. 后处理的Warp分化严重（占25%时间）
> 
> **阶段2：Kernel融合优化**
> - 将5个独立的小Kernel融合成2个大Kernel
> - 消除了中间结果的全局内存读写
> - 节省11ms
> 
> **阶段3：内存优化**
> - 将卷积核权重用常量内存存储
> - 使用共享内存实现输入特征图的块缓存
> - 优化合并访问模式
> - 节省15ms
>

> - 重构后处理的条件判断
> - 使用查表法替代分支
> - 分支效率从62%提升到98%
> - 节省6ms
> 
> **阶段5：指令级优化**
> - 使用CUDA Math Library的快速函数
> - 循环展开，增加指令级并行
> - 节省2ms
> 
> **最终结果**：
> - 单帧处理时间：42ms → 8ms
> - 性能提升：5.25倍
> - 满足30fps实时要求
> 
> **最大挑战**：
> 最大的挑战是Kernel融合后的寄存器压力。融合后寄存器使用量激增，导致Occupancy从80%降到30%。
> 
> 解决方案：
> 1. 将部分不需要跨迭代的变量移到共享内存
> 2. 使用--maxrregcount编译器选项限制寄存器使用
> 3. 对关键循环进行寄存器分配分析
> 最终Occupancy恢复到65%，找到了平衡点。
> 
> **反思与改进**：
> 如果重新做这个项目，我会：
> 
> 1. **更早引入性能建模**：在编码前就用roofline模型估算理论上限，避免盲目优化
> 
> 2. **采用增量式优化**：之前是一次性做了很多改动，出问题很难定位。现在我会每次只改一个点，测量验证后再继续
> 
> 3. **更重视数据布局设计**：最初的数据布局（AoS）导致了很多不必要的转置操作。应该在项目初期就考虑数据布局对性能的影响
> 
> 4. **建立性能回归测试**：优化过程中几次出现了正确性问题。应该有一套自动化的性能+正确性测试，每次提交都运行
> 
> 5. **考虑硬件特性**：当时针对T4优化，后来部署到A10时没有充分利用Tensor Core。应该在设计时就考虑硬件特性，提供不同路径
> 
> 这个项目让我深刻理解了，性能优化不是一蹴而就的，需要系统性的方法和耐心的迭代。

#### 满分回答示例
> **核心架构差异**：
> 
> | 维度 | CPU | GPU |
> |------|-----|-----|
> | **设计目标** | 低延迟通用计算 | 高吞吐并行计算 |
> | **核心数量** | 少（几到几十个） | 多（几千到上万个） |
> | **缓存** | 大缓存（MB级），优化延迟 | 小缓存，优化带宽 |
> | **控制逻辑** | 复杂，支持复杂分支 | 简单，SIMT执行 |
> | **执行模型** | MIMD，每个核独立 | SIMT，线程束执行 |
> 
> **对编程模型的影响**：
> 
> 1. **并行粒度**：
>    - CPU：粗粒度并行，进程/线程级
>    - GPU：细粒度并行，线程/线程束级
> 
> 2. **分支处理**：
>    - CPU：分支预测，乱序执行
>    - GPU：线程束分化，串行执行不同分支
> 
> 3. **内存模型**：
>    - CPU：统一内存，硬件缓存一致性
>    - GPU：多层内存层次，需要软件管理
> 
> 4. **同步机制**：
>    - CPU：原子操作、锁、条件变量
>    - GPU：__syncthreads()、原子操作、流同步
> 
> **适合GPU加速的问题特征**：
> 
> 1. **数据并行性高**：大量数据可以独立处理
>    - 图像处理：每个像素独立计算
>    - 矩阵运算：每个元素/行/列独立
> 
> 2. **计算密集型**：算术强度（计算量/数据量）高
>    - 密码破解：大量哈希计算
>    - 数值模拟：大量浮点运算
> 
> 3. **规则的内存访问模式**：有良好的空间局部性
>    - 连续数组访问
>    - 结构化网格计算
> 
> 4. **高吞吐优先于低延迟**：
>    - 批处理任务
>    - 离线处理
> 
> **不适合GPU的场景**：
> 
> 1. **控制流复杂**：大量不可预测的分支
> 2. **数据相关性强**：并行度低
> 3. **小数据量**：数据传输开销大于加速收益
> 4. **需要极低延迟**：GPU调度有开销
> 
> **判断框架**：
> 我通常用三个问题来判断：
> 1. 能否分解成数千个独立任务？
> 2. 每个任务的计算量是否显著大于内存访问量？
> 3. 端到端时间是否足够长（>100µs）来摊销GPU开销？

### 问题2：Tensor Core原理与应用

#### 面试官追问层级
- **L1**：什么是Tensor Core？
- **L2**：Tensor Core的工作原理是什么？
- **L3**：如何在实际应用中有效利用Tensor Core？

#### 评分标准（0-5分）
| 分数 | 打分点说明 |
|------|-----------|
| 0分 | 没听说过Tensor Core |
| 1分 | 知道Tensor Core用于AI |
| 2分 | 了解Tensor Core做矩阵乘法 |
| 3分 | 能说明WMMA的工作原理 |
| 4分 | 能使用WMMA API编程 |
| 5分 | 能设计高效的Tensor Core应用 |

#### 满分回答示例
> **什么是Tensor Core**：
> Tensor Core是NVIDIA从Volta架构开始引入的专用硬件单元，用于执行混合精度矩阵乘法和累加（MMA）运算。
> 
> **性能指标**：
> - A100 FP16：312 TFLOPS
> - A100 Tensor Core FP16：624 TFLOPS
> - A100 Tensor Core TF32：312 TFLOPS
> - 比普通CUDA核心快8-16倍
> 
> **工作原理**：
> 
> 1. **Warp级矩阵运算（WMMA）**：
>    - 一个Warp（32线程）协作完成一个矩阵乘法
>    - 标准大小：16x16x16 FP16
>    - D = A × B + C
> 
> 2. **数据布局要求**：
>    - 矩阵必须按特定格式布局
>    - 支持多种布局：行列主序、转置
>    - 需要对齐到16字节边界
> 
> **WMMA API使用**：
> ```cuda
> #include <mma.h>
> using namespace nvcuda;
> 
> __global__ void wmma_kernel(half* A, half* B, float* C, int M, int N, int K) {
>     // 定义fragment
>     wmma::fragment<wmma::matrix_a, 16, 16, 16, half, wmma::col_major> a_frag;
>     wmma::fragment<wmma::matrix_b, 16, 16, 16, half, wmma::row_major> b_frag;
>     wmma::fragment<wmma::accumulator, 16, 16, 16, float> c_frag;
>     
>     // 初始化accumulator
>     wmma::fill_fragment(c_frag, 0.0f);
>     
>     // 计算tile索引
>     int tile_row = blockIdx.y;
>     int tile_col = blockIdx.x;
>     
>     for (int k = 0; k < K; k += 16) {
>         // 加载数据
>         wmma::load_matrix_sync(a_frag, A + tile_row*16 + k*M, M);
>         wmma::load_matrix_sync(b_frag, B + k + tile_col*16*K, K);
>         
>         // 执行MMA
>         wmma::mma_sync(c_frag, a_frag, b_frag, c_frag);
>     }
>     
>     // 存储结果
>     wmma::store_matrix_sync(C + tile_row*16 + tile_col*N, c_frag, N, 
>                             wmma::mem_row_major);
> }
> ```
> 
> **高效利用Tensor Core的策略**：
> 
> 1. **选择合适的Tile大小**：
>    - 16x16x16：基础大小，兼容性好
>    - 32x8x16 / 8x32x16：适合特定形状
>    - 更大的Tile可以提高计算密度
> 
> 2. **数据预取和流水线**：
> ```cuda
> // 双缓冲：计算当前tile的同时预取下一个
> wmma::load_matrix_sync(a_frag[0], ...);
> for (int k = 0; k < K; k += 16) {
>     wmma::load_matrix_sync(a_frag[1], ...);  // 预取
>     wmma::mma_sync(c_frag, a_frag[0], b_frag, c_frag);  // 计算
>     swap(a_frag[0], a_frag[1]);
> }
> ```
> 
> 3. **精度选择**：
>    - FP16：最快，适合推理
>    - TF32：平衡速度和精度，适合训练
>    - FP32/FP64：需要时用，但性能下降
> 
> 4. **与CUDA Core混合使用**：
>    - Tensor Core处理矩阵乘法
>    - CUDA Core处理后处理、激活函数等
> 
> 5. **使用cuBLASLT和CUTLASS**：
>    - 对于标准矩阵乘法，直接用高度优化的库
>    - 比自己写WMMA性能更好
> 
> **实际应用案例**：
> 在优化Transformer推理时，我将自注意力中的QK^T矩阵乘法改用WMMA实现。
> - 原始CUDA实现：seq_len=128时，128µs
> - Tensor Core实现：24µs
> - 性能提升：5.3倍
> 
> 关键优化点：
> 1. 将Q/K从FP32转成FP16存储
> 2. 使用双缓冲隐藏内存延迟
> 3. 合理的Tile大小（32x32x16）
> 4. 与Softmax Kernel融合，避免中间结果写回全局内存

#### 反面教材示例
> Tensor Core就是AI用的，做矩阵乘法很快。用cuBLAS就行，不用自己写。

### 问题3：多GPU编程模型

#### 面试官追问层级
- **L1**：多GPU编程有哪些模型？
- **L2**：NVLink vs PCIe的差异是什么？
- **L3**：如何设计高效的多GPU系统？

#### 评分标准（0-5分）
| 分数 | 打分点说明 |
|------|-----------|
| 0分 | 没做过多GPU |
| 1分 | 知道多GPU的存在 |
| 2分 | 用过简单的多GPU |
| 3分 | 理解不同编程模型 |
| 4分 | 能分析通信开销 |
| 5分 | 能设计复杂的多GPU系统 |

#### 满分回答示例
> **多GPU编程模型**：
> 
> **1. 单程序多数据（SPMD）**：
> - 每个GPU运行相同的程序，处理不同的数据
> - 使用cudaSetDevice()切换GPU
> - 适合数据并行场景
> ```cuda
> #pragma omp parallel for num_threads(N_GPU)
> for (int gpu = 0; gpu < N_GPU; gpu++) {
>     cudaSetDevice(gpu);
>     process_data(data[gpu]);
> }
> ```
> 
> **2. 对等访问（Peer-to-Peer, P2P）**：
> - GPU之间直接访问对方的内存
> - 需要NVLink或PCIe支持
> ```cuda
> // 启用对等访问
> cudaDeviceEnablePeerAccess(other_gpu, 0);
> 
> // 直接访问其他GPU的内存
> cudaMemcpy(dst_dev_ptr, src_dev_ptr_on_other_gpu, size, 
>            cudaMemcpyDeviceToDevice);
> ```
> 
> **3. NCCL（NVIDIA Collective Communications Library）**：
> - 专为GPU设计的集合通信库
> - 支持AllReduce、Broadcast、AllGather等
> - 自动利用NVLink和PCIe拓扑
> ```cuda
> ncclComm_t comm;
> ncclCommInitAll(&comm, N_GPU, gpu_list);
> 
> ncclAllReduce(sendbuf, recvbuf, count, ncclFloat, 
>               ncclSum, comm, stream);
> ```
> 
> **4. MPI+CUDA**：
> - 传统的MPI多进程，每个进程控制一个GPU
> - 适合大规模分布式训练
> 
> **NVLink vs PCIe**：
> 
> | 特性 | PCIe 4.0 x16 | NVLink 4.0 (单链路) |
> |------|-------------|---------------------|
> | **带宽** | ~32 GB/s | ~900 GB/s |
> | **延迟** | ~1-2µs | ~0.3µs |
> | **GPU间通信** | 需要CPU参与 | 直接通信 |
> | **内存一致性** | 不保证 | 保证 |
> | **P2P支持** | 部分支持 | 完全支持 |
> 
> **高效多GPU系统设计**：
> 
> **1. 数据划分策略**：
> ```
> 模型并行（按层划分）
>     ↓
> 数据并行（按batch划分）← 最常用，扩展性好
>     ↓
> 流水线并行（按阶段划分）
> ```
> 
> **2. 通信隐藏**：
> - 使用CUDA流将计算与通信重叠
> ```cuda
> // 计算本批次的同时，通信下一批次
> compute<<<grid, block, 0, stream[0]>>>(current_data);
> ncclAllReduce(..., stream[1]);  // 并行进行
> ```
> 
> **3. 拓扑感知**：
> - 查询GPU拓扑结构，选择最优通信路径
> ```cuda
> cudaDeviceProp prop;
> cudaGetDeviceProperties(&prop, gpu_id);
> // 检查peer access能力
> int can_access_peer;
> cudaDeviceCanAccessPeer(&can_access_peer, gpu1, gpu2);
> ```
> 
> **4. 负载均衡**：
> - 均匀分配计算任务
> - 考虑异构GPU的性能差异
> - 动态负载调度
> 
> **5. 内存优化**：
> - 减少不必要的数据传输
> - 使用NVLink时可以共享大内存
> - 考虑统一内存（UM）简化编程
> 
> **实际案例**：
> 我设计过一个8GPU的推荐系统训练系统：
> 
> 架构：
> - 2台DGX A100（每台4GPU）
> - 机器间：InfiniBand 200G

### 问题4：统一内存（Unified Memory）

#### 面试官追问层级
- **L1**：什么是统一内存？
- **L2**：统一内存的工作原理是什么？
- **L3**：统一内存的性能开销和适用场景？

#### 评分标准（0-5分）
| 分数 | 打分点说明 |
|------|-----------|
| 0分 | 不知道统一内存 |
| 1分 | 听说过统一内存 |
| 2分 | 知道cudaMallocManaged |
| 3分 | 理解页面迁移机制 |
| 4分 | 能分析性能开销 |
| 5分 | 能合理使用统一内存优化开发效率 |

#### 满分回答示例
> **什么是统一内存**：
> 统一内存（UM）是CUDA 6.0引入的特性，提供一个单一的内存地址空间，CPU和GPU都可以通过同一个指针访问数据。系统自动处理数据在CPU和GPU之间的迁移。
> 
> **使用方法**：
> ```cuda
> // 分配统一内存
> float* data;
> cudaMallocManaged(&data, size * sizeof(float));
> 
> // CPU直接访问
> for (int i = 0; i < size; i++) {
>     data[i] = i;  // CPU直接写
> }
> 
> // GPU直接访问
> kernel<<<grid, block>>>(data);  // GPU直接读
> 
> // 不需要cudaMemcpy！
> ```
> 
> **工作原理**：
> 
> 1. **页面故障机制**：
>    - UM分配时不实际分配物理内存
>    - 首次访问时触发页面故障
>    - 按需分配物理页面
> 
> 2. **页面迁移（Pascal及之后）**：
>    - GPU访问不在GPU内存的页面 → 触发迁移
>    - 使用DMA在后台迁移整个页面
>    - 4KB页面大小
> 
> 3. **按需分页（On-demand Paging）**：
>    - 只迁移实际访问的页面
>    - 不访问的不占用内存
> 
> 4. **内存过量提交（Over-subscription）**：
>    - 可以分配超过GPU显存大小的UM
>    - 系统自动在CPU/GPU之间换页
> 
> **性能开销分析**：
> 
> | 场景 | 开销 |
> |------|------|
> | 首次CPU访问 | 小（只分配CPU内存） |
> | 首次GPU访问 | 中（CPU→GPU迁移） |
> | 再次CPU访问 | 大（GPU→CPU迁移） |
> | 细粒度交替访问 | 很大（乒乓效应） |
> 
> **性能优化策略**：
> 
> 1. **预取（Prefetching）**：
> ```cuda
> // 提前将数据迁移到GPU
> cudaMemPrefetchAsync(data, size, gpu_id, stream);
> 
> // 提前迁移回CPU
> cudaMemPrefetchAsync(data, size, cudaCpuDeviceId, stream);
> ```
> 
> 2. **建议使用位置（Usage Hints）**：
> ```cuda
> // 提示数据主要在GPU访问
> cudaMemAdvise(data, size, cudaMemAdviseSetPreferredLocation, gpu_id);
> 
> // 提示数据只读，不需要回写
> cudaMemAdvise(data, size, cudaMemAdviseSetReadMostly, gpu_id);
> ```
> 
> 3. **避免细粒度共享**：
> ```cuda
> // 不好：交替读写，大量页面迁移
> for (int i = 0; i < 100; i++) {
>     kernel<<<1, 32>>>(data);  // GPU访问
>     cudaDeviceSynchronize();
>     data[0] += 1;             // CPU访问
> }
> ```
> 
> 4. **大块数据处理**：
> - UM对大块数据效率较高
> - 小块数据（<几MB）迁移开销相对较大
> 
> **适用场景**：
> 
> ✅ **适合的场景**：
> 1. **快速原型开发**：不需要考虑内存管理，开发效率高
> 2. **复杂数据结构**：链表、树、图等，手动复制困难
> 3. **动态数据结构**：大小动态变化的数据
> 4. **多GPU共享数据**：数据需要在多个GPU间共享
> 5. **内存过量提交**：数据量超过GPU显存，但访问有局部性
> 
> ❌ **不适合的场景**：
> 1. **性能关键路径**：需要最大性能的地方
> 2. **细粒度CPU/GPU交互**：频繁交替访问
> 3. **可预测的访问模式**：能明确知道数据流向时，显式复制更快
> 
> **实际经验**：
> 我在开发一个图形应用时使用了UM：
> 
> - 场景：复杂的场景图，包含各种几何体和材质
> - 传统方案：手动管理CPU/GPU双副本，同步逻辑复杂，代码量大
> - UM方案：代码量减少60%，开发时间缩短一半
> - 性能：只比手动优化版本慢8%，完全可接受
> 
> 结论：UM是开发效率的利器，但在追求极致性能时，配合预取和advice使用，或者用显式复制。

#### 反面教材示例
> 统一内存就是cudaMallocManaged，不用管数据在哪里，CPU和GPU都能访问，很方便。

> **调试CUDA程序的方法**：
> 
> **第一层：基础错误检查**
> 
> 1. **总是检查CUDA错误码**：
> ```cuda
> #define CHECK_CUDA(err) \
>     if (err != cudaSuccess) { \
>         fprintf(stderr, "CUDA error at %s:%d: %s\n", \
>                 __FILE__, __LINE__, cudaGetErrorString(err)); \
>         exit(EXIT_FAILURE); \
>     }

> CHECK_CUDA(cudaMalloc(&dev_ptr, size));

> // 检查Kernel错误（Kernel本身不返回错误码）
> kernel<<<grid, block>>>(...);
> CHECK_CUDA(cudaGetLastError());  // 检查launch错误
> CHECK_CUDA(cudaDeviceSynchronize());  // 检查执行错误
> ```
> 
> 2. **启用同步模式**：
> ```bash
> # 让所有CUDA操作同步执行，更容易定位错误
> export CUDA_LAUNCH_BLOCKING=1

> **第二层：内存错误检查**

> 1. **cuda-memcheck**：

> # 检查内存越界、未初始化访问等
> cuda-memcheck ./application
> 
> # 更详细的内存检查
> cuda-memcheck --tool memcheck --leak-check full ./app
> 
> # 检查race condition
> cuda-memcheck --tool racecheck ./app
> 
> # 检查未初始化变量
> cuda-memcheck --tool initcheck ./app
> ```
> 
> 2. **常见内存错误**：
> - 写越界：访问超过分配的内存范围
> - 读越界：读取未分配的内存
> - 未初始化内存访问：读取未写入的内存
> - 重复释放：多次cudaFree同一个指针
> - 释放无效指针：释放不是cudaMalloc的指针

> 
> 1. **cuda-gdb（Linux）**：
> ```bash

> 
> # 常用命令
> break kernel_name          # 在Kernel入口设断点

> - 查看内存、寄存器、共享内存
> 
> **第四层：处理并发问题**
> 
> **并发问题的特点**：
> - 难以复现：执行顺序不确定
> - Heisenbug：加了debug信息问题就消失
> - 症状随机：有时崩溃，有时结果错误
> 
> **处理方法论**：
> 
> 1. **简化问题**：
>    - 减少线程数：从1线程开始，逐渐增加
>    - 减小问题规模：用小数据集测试
>    - 禁用优化：-O0编译，便于调试
> 
> 2. **强制确定性**：
> ```bash
> # 让GPU执行更确定（影响性能）
> export CUDA_VISIBLE_DEVICES=0
> export CUDA_LAUNCH_BLOCKING=1
> ```
> 
> 3. **日志与追踪**：
> ```cuda
> // 线程安全的日志（输出到缓冲区，避免乱序）
> __device__ void log(int tid, const char* msg) {
>     atomicAdd(&log_head, 1);
>     log_buffer[log_head] = ...;
> }
> ```
> 
> 4. **确定性重放**：
> - 记录关键操作的顺序
> - 用相同的种子重放
> 
> 5. **使用racecheck工具**：
> ```bash
> cuda-memcheck --tool racecheck --racecheck-report analysis ./app
> ```
> 
> **常见CUDA错误分类**：
> 
> | 错误类型 | 典型症状 | 排查方法 |
> |----------|---------|---------|
> | **配置错误** | invalid configuration argument | 检查grid/block大小 |
> | **内存越界** | unspecified launch failure | cuda-memcheck |
> | **同步错误** | 偶尔结果错误 | racecheck，简化 |
> | **资源耗尽** | out of memory | 检查分配大小 |
> | **设备不支持** | invalid device function | 检查计算能力 |
> 
> **真实案例**：
> 我遇到过一个难以复现的Bug：
> 
> 症状：
> - 大数据集时偶尔崩溃
> - 加printf就不崩溃
> - 不同机器崩溃频率不同
> 
> 排查过程：
> 1. 先用cuda-memcheck，没发现问题
> 2. 用racecheck，发现有潜在的warp内数据竞争
> 3. 简化到只有一个block，问题稳定复现
> 4. 发现是__shfl_sync()的使用错误：没有正确mask
> 
> 原因：
> ```cuda
> // Bug：假设warp是完整的，但最后一个warp可能不完整
> val = __shfl_xor_sync(0xffffffff, val, 16);
> 
> // 修复：使用正确的active mask
> unsigned int mask = __activemask();
> val = __shfl_xor_sync(mask, val, 16);
> ```
> 
> 教训：
> - 并发问题很难，必须有系统的方法
> - 简化是关键，从小规模开始
> - 工具很重要，但理解原理更重要
