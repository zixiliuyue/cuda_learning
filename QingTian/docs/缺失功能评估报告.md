# QingTian（擎天）平台缺失功能评估报告

**文档版本**: v1.0  
**评估日期**: 2026-07-21  
**评估范围**: 后端核心、前端控制台、基础设施集成

---

## 1. 执行摘要

### 1.1 当前成熟度评估

| 评估维度 | 成熟度 | 说明 |
|---------|--------|------|
| **单机调度能力** | 85% | 单机多卡调度、任务生命周期、资源账本基本完善 |
| **可观测性** | 80% | 日志流、计量计费、Dashboard 已具备 |
| **用户界面** | 75% | 核心功能界面完成，但缺少可视化编排 |
| **基础设施集成** | 30% | **最大短板**：缺少 Kubernetes 原生支持 |
| **分布式训练** | 20% | 仅单机调度，无多机多卡 Gang Scheduling |
| **多租户隔离** | 25% | 项目级隔离，缺少 Namespace/网络隔离 |

### 1.2 关键结论

> **核心判断**：QingTian 目前是一个**功能完整的单机 GPU 调度平台**，但要成为**企业级分布式 AI 基础设施**，必须补全 **Kubernetes 深度集成** 这一核心能力。

**预期收益**：
- 与 GitOps 工作流集成（Flux/ArgoCD）

#### 2.2 Gang Scheduling（多机多卡分布式训练）

| 属性 | 说明 |
|------|------|
| **现状** | 仅支持单机多卡（单个 Pod/Container）|
| **缺失原因** | 调度器未实现 PodGroup / Gang Scheduling 语义 |
| **影响范围** | 无法运行需要多机通信的分布式训练（DDP、DeepSpeed、Horovod）|

**详细需求**：

```go
// 期望的 Gang Scheduling 语义
type PodGroup struct {
    Name string
    Spec PodGroupSpec
    Status PodGroupStatus
}

type PodGroupSpec struct {
    MinMember int32           // 最少需要调度的 Pod 数
    Scheduler string          // 使用哪个调度器
    PriorityClassName string  // 优先级
}

// 调度策略：All-or-Nothing
// 要么全部调度成功，要么一个都不调度
// 防止资源死锁（部分 Pod 占用资源等待其他 Pod，但其他 Pod 无法调度）
```

**实现方案**：

1. **集成 Volcano Scheduler**（推荐）
   - Volcano 是 CNCF 项目，原生支持 Gang Scheduling
   - 提供 PodGroup、Queue、Priority 等高级调度语义
   - 与 QingTian 调度器共存：Volcano 负责多机 Gang，QingTian 负责单机精细调度

2. **自研 Gang Scheduler**（备选）
   ```go
   // 核心逻辑：两阶段提交
   type GangScheduler struct {
       pendingGroups map[string]*PodGroup
       reservedNodes map[string][]string // group -> node list
   }

   func (gs *GangScheduler) Schedule(pg *PodGroup) error {
       // 阶段1：预留资源（不真正分配）
       nodes, err := gs.reserve(pg)
       if err != nil {
           return err // 资源不足，直接失败
       }
       
       // 阶段2：原子分配
       if err := gs.commit(pg, nodes); err != nil {
           gs.rollback(pg) // 回滚
           return err
       }
       return nil
   }
   ```

**预期收益**：
- 支持千亿参数大模型训练（需要 100+ GPU 分布式）
- 提高集群利用率（避免资源碎片导致的无法调度）
- 支持主流训练框架（PyTorch DDP、DeepSpeed、Megatron-LM、Horovod）

#### 2.3 多租户 Namespace/网络隔离

| 属性 | 说明 |
|------|------|
| **现状** | 仅有项目级逻辑隔离，无物理/网络隔离 |
| **缺失原因** | 未集成 Kubernetes NetworkPolicy / CNI 隔离 |
| **影响范围** | 无法保障多用户环境下的安全和资源隔离 |

**详细需求**：

```yaml
# 多租户隔离模型
---
# 1. Namespace 隔离
apiVersion: v1
kind: Namespace
metadata:
  name: team-a-project-1
  labels:
    qingtian.io/tenant: team-a
    qingtian.io/project: project-1
    qingtian.io/resource-quota: gpu-8

---
# 2. 资源配额
apiVersion: v1
kind: ResourceQuota
metadata:
  name: gpu-quota
  namespace: team-a-project-1
spec:
  hard:
    requests.nvidia.com/gpu: 8
    limits.nvidia.com/gpu: 8
    requests.memory: 128Gi

---
# 3. 网络隔离（NetworkPolicy）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: team-a-project-1
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress

---
# 4. 允许同项目内通信
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-same-project
  namespace: team-a-project-1
spec:
  podSelector:
    matchLabels:
      qingtian.io/project: project-1
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              qingtian.io/project: project-1
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              qingtian.io/project: project-1
```

**实现建议**：

1. **Namespace 自动管理**
   ```go
   type NamespaceManager struct {
       k8sClient kubernetes.Interface
   }

   func (nm *NamespaceManager) CreateWorkspace(tenant, project string) (*v1.Namespace, error) {
       ns := &v1.Namespace{
           ObjectMeta: metav1.ObjectMeta{
               GenerateName: fmt.Sprintf("%s-%s-", tenant, project),
               Labels: map[string]string{
                   "qingtian.io/tenant":  tenant,
                   "qingtian.io/project": project,
               },
           },
       }
       return nm.k8sClient.CoreV1().Namespaces().Create(context.TODO(), ns, metav1.CreateOptions{})
   }
   ```

2. **CNI 网络隔离**
   - 使用 Calico 或 Cilium 作为 CNI
   - 基于 Label 的 NetworkPolicy 自动生成
   - 支持跨 Namespace 通信白名单

3. **资源配额自动同步**
   - 当用户在控制台修改配额时，自动同步到 K8s ResourceQuota
   - 支持 GPU 显存配额（使用 Extended Resources）

**预期收益**：
- 满足金融/医疗等强隔离要求行业需求
- 防止租户间资源抢占和干扰
- 支持复杂的网络策略（如只允许访问特定存储）

#### 2.4 监控告警与可观测性增强

| 属性 | 说明 |
|------|------|
| **现状** | 基础日志流和 Dashboard，无告警机制 |
| **缺失原因** | 未集成 Prometheus/Grafana 生态 |
| **影响范围** | 无法主动发现问题，依赖用户反馈 |

**详细需求**：

```yaml
# 监控指标定义
metrics:
  # 基础设施层
  - node_gpu_utilization      # GPU 利用率
  - node_gpu_memory_used      # GPU 显存使用
  - node_gpu_temperature      # GPU 温度
  - node_power_draw          # 功耗
  
  # 调度层
  - scheduler_queue_length    # 调度队列长度
  - scheduler_wait_time       # 平均等待时间
  - scheduling_latency        # 调度延迟
  
  # 任务层
  - task_duration            # 任务执行时长
  - task_gpu_hours           # GPU 小时消耗
  - task_failure_rate        # 任务失败率
  - task_retry_count         # 重试次数

# 告警规则
alerts:
  - name: GPU温度过高
    condition: node_gpu_temperature > 85
    duration: 5m
    severity: warning
    
  - name: 任务失败率过高
    condition: rate(task_failure_rate[5m]) > 0.1
    duration: 10m
    severity: critical
    
  - name: 调度队列积压
    condition: scheduler_queue_length > 100
    duration: 15m
    severity: warning
    
  - name: GPU 利用率低（资源浪费）
    condition: node_gpu_utilization < 10
    duration: 1h
    severity: info
```

**实现建议**：

1. **Prometheus Exporter**
   ```go
   type MetricsExporter struct {
       gpuUtilization  *prometheus.GaugeVec
       taskDuration    *prometheus.HistogramVec
   }

   func NewMetricsExporter() *MetricsExporter {
       return &MetricsExporter{
           gpuUtilization: prometheus.NewGaugeVec(
               prometheus.GaugeOpts{
                   Name: "qingtian_gpu_utilization_percent",
                   Help: "GPU utilization percentage",
               },
               []string{"node", "gpu_uuid", "gpu_index"},
           ),
           taskDuration: prometheus.NewHistogramVec(
               prometheus.HistogramOpts{
                   Name:    "qingtian_task_duration_seconds",
                   Help:    "Task execution duration",
                   Buckets: prometheus.DefBuckets,
               },
               []string{"status", "gpu_model"},
           ),
       }
   }
   ```

2. **Grafana Dashboard**
   - 导入官方 GPU 监控模板（如 nvidia-dcgm-exporter Dashboard）
   - 自定义 QingTian 专属面板：
     - 资源总览：节点数、GPU 总数、在线率
     - 调度看板：队列长度、等待时间、调度成功率
     - 任务分析：任务分布、成功率趋势、资源消耗 Top10
     - 告警面板：当前活跃告警、历史告警统计

3. **告警通道**
   - Alertmanager 集成：邮件、钉钉、飞书、PagerDuty
   - 告警分级：Info/Warning/Critical，不同级别不同通知方式
   - 告警抑制：同类告警合并，避免告警风暴

**预期收益**：
- 主动发现 GPU 故障、任务异常，降低 MTTR（平均修复时间）
- 资源利用率可视化，辅助容量规划
- 基于历史数据的调度策略优化

#### 2.7 弹性伸缩（HPA/VPA）

| 属性 | 说明 |
|------|------|
| **现状** | 资源静态分配，无自动扩缩容 |
| **缺失原因** | 未实现基于队列长度或 GPU 利用率的伸缩策略 |
| **影响范围** | 高峰期任务排队，低峰期资源浪费 |

**详细需求**：

```yaml
# 弹性伸缩配置
features:
  # 1. 水平伸缩（HPA）- 基于队列长度
  hpa:
    triggers:
      - type: queue-length
        metric: scheduler.queue.length
        target: 10  # 队列长度超过10则扩容
        scaleUpStep: 2  # 每次扩容2个节点
      - type: gpu-utilization
        metric: node.gpu.utilization
        target: 80%
        scaleDownDelay: 10m  # 10分钟后才缩容
    limits:
      minNodes: 3
      maxNodes: 100

  # 2. 垂直伸缩（VPA）- 基于历史资源使用
  vpa:
    recommendationMode: Auto
    updateMode: Initial  # 仅在 Pod 创建时调整，运行中不重启
    resources:
      cpu:
        minAllowed: 100m
        maxAllowed: 4
      memory:
        minAllowed: 256Mi
        maxAllowed: 64Gi

  # 3. 预测性伸缩（基于历史模式）
  predictive:
    enabled: true
    model: "time-series-forecasting"  # 使用时间序列预测
    horizon: "1h"  # 预测未来1小时负载
    trainingData: "30d"  # 使用30天历史数据训练
```
