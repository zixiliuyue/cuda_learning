# 诊断决策树：内存带宽低

---

## 快速导航

```
发现内存带宽低
  │
  ├─▶ 步骤1: 确认硬件理论带宽
  ├─▶ 步骤2: 分析内存访问类型
  │       ├─▶ 全局内存 → 分支A
  │       ├─▶ 共享内存 → 分支B
  │       └─▶ 常量/纹理内存 → 分支C
  │
  ├─▶ 步骤3: 定位具体问题
  └─▶ 步骤4: 优化并验证
```

---

## 诊断流程详解

### 阶段一：基准线确认

#### 步骤1: 确认硬件理论带宽

```
查询GPU型号，获取理论带宽
  │
  ├─▶ 计算方式:
  │   理论带宽 (GB/s) = 显存频率 (GHz) × 显存位宽 (bit) / 8
  │
  ├─▶ 示例:
  │   A100: 1.593 GHz × 5120 bit / 8 = 1555 GB/s (HBM2)
  │   RTX3090: 9.75 GHz × 384 bit / 8 = 936 GB/s (GDDR6X)
  │
  └─▶ 确认实际测量带宽
      ├─▶ 使用 cudaMemcpy 带宽测试（Host<->Device）
      ├─▶ 使用简单内核测试 Device<->DRAM 带宽
      └─▶ 与理论值对比，确定差距大小
```

**简单带宽测试内核**：
```cpp
__global__ void copy_kernel(float* dst, const float* src, int n) {
    int idx = blockIdx.x * 256 + threadIdx.x;
    if (idx < n) {
        dst[idx] = src[idx];
    }
}
```

---

### 阶段二：整体内存使用分析

#### 检查1: 内存访问是否饱和

```
使用 Nsight Compute 查看内存吞吐量
  │
  ├─▶ DRAM读取/写入吞吐量 < 理论峰值的 50%?
  │   └─▶ 内存控制器未充分利用，需要深入分析
  │
  ├─▶ DRAM吞吐量在 50-80% 之间?
  │   └─▶ 部分利用，可能还有优化空间
  │
  └─▶ DRAM吞吐量 > 80%?
      └─▶ 内存带宽已经充分利用
          ├─▶ 如果性能仍不满足，需要算法层面减少访存
          └─▶ 考虑使用更高带宽的GPU
```

---

#### 检查2: 读写比例分析

```
查看读取和写入的比例
  │
  ├─▶ 读取远多于写入（读密集）
  │   ├─▶ 考虑数据压缩
  │   ├─▶ 增加数据重用（共享内存/L1）
  │   └─▶ 优化只读访问模式（如常量内存）
  │
  ├─▶ 写入远多于读取（写密集）
  │   ├─▶ 检查是否可以合并写入
  │   ├─▶ 考虑流式写入（不经过L1）
  │   └─▶ 减少不必要的写回
  │
  └─▶ 读写大致平衡
      └─▶ 需要分别优化读取和写入
```

---

### 阶段三：具体问题诊断

#### 分支A: 全局内存问题

**诊断A1: 检查合并访问**
```
查看 gld_transactions_per_request（全局加载每次请求的事务数）
  │
  ├─▶ 值 ≈ 1.0
  │   └─▶ ✅ 合并访问良好
  │
  ├─▶ 1.0 < 值 < 4
  │   └─▶ ⚠️  部分非合并，有优化空间
  │
  └─▶ 值 > 4
      └─▶ ❌ 严重非合并，需要重点优化
          ├─▶ 检查索引计算
          │   ├─▶ 是否为 idx = block * blockDim + threadIdx.x?
          │   ├─▶ 2D索引是否正确：row * width + col?
          │   └─▶ 是否有跨步访问 idx * stride?
          │
          ├─▶ 检查数据布局
          │   ├─▶ 是否使用了结构体数组(AoS)?
          │   └─▶ 考虑改为数组的结构体(SoA)
          │
          └─▶ 检查访问模式
              ├─▶ 是否有间接索引 data[indices[idx]]?
              ├─▶ 是否有乱序访问?
              └─▶ 是否可以重新排序数据?
```

**代码示例：修复非合并访问**

```cpp
// ❌ 非合并访问：AoS（结构体数组）
struct PointAoS { float x, y, z; };
__global__ void bad_access(PointAoS* points, int n) {
    int idx = blockIdx.x * 256 + threadIdx.x;
    if (idx < n) {
        float x = points[idx].x;  // 每个线程间隔12字节访问
        // 计算...
    }
}

// ✅ 合并访问：SoA（数组的结构体）
struct PointsSoA { float* x; float* y; float* z; };
__global__ void good_access(PointsSoA points, int n) {
    int idx = blockIdx.x * 256 + threadIdx.x;
    if (idx < n) {
        float x = points.x[idx];  // 连续4字节访问
        // 计算...
    }
}
```

---

**诊断A2: 检查L1/L2缓存命中率**
```
查看 l1_cache_global_hit_rate 和 l2_cache_hit_rate
  │
  ├─▶ L1命中率 < 30%?
  │   └─▶ L1缓存未充分利用
  │       ├─▶ 是否使用了更多的L1而不是共享内存?
  │       ├─▶ 访问模式是否太随机?
  │       └─▶ 考虑分块(Tiling)提高局部性
  │
  ├─▶ L2命中率 < 50%?
  │   └─▶ L2缓存未充分利用
  │       ├─▶ 数据重用是否跨Block?
  │       ├─▶ 考虑调整Block处理顺序
  │       └─▶ 减少工作集大小
  │
  └─▶ 命中率都很高但带宽仍低?
      └─▶ 可能不是缓存问题
          ├─▶ 检查是否有足够的并行请求
          └─▶ 检查是否内存控制器分区不平衡
```

---

**诊断A3: 检查内存访问粒度**
```
查看是否使用向量加载/存储
  │
  ├─▶ 是否使用 float2/float4 向量类型?
  │   ├─▶ 是 → 向量加载效率更高
  │   └─▶ 否 → 考虑向量化
  │
  └─▶ 每个线程加载的数据量是否足够?
      ├─▶ 每个线程只加载1个元素可能效率低
      └─▶ 考虑每个线程加载4-16个元素
```

**向量加载示例**：
```cpp
__global__ void vector_load(float4* dst, const float4* src, int n) {
    int idx = blockIdx.x * 64 + threadIdx.x;
    if (idx < n) {
        dst[idx] = src[idx];  // 一次加载16字节
    }
}
```

#### 分支B: 共享内存问题

**诊断B1: 检查Bank冲突**
```
查看 shared_efficiency（共享内存效率）
  │
  ├─▶ shared_efficiency > 90%
  │   └─▶ ✅ 共享内存效率良好
  │
  ├─▶ shared_efficiency < 70%
  │   └─▶ ❌ Bank冲突严重
  │       ├─▶ 检查访问步长是否为32的约数
  │       ├─▶ 检查2D数组的行列访问
  │       ├─▶ 考虑添加填充（如 [32][33]）
  │       └─▶ 调整数据结构
  │
  └─▶ 查看 shared_load_transactions_per_request
      ├─▶ > 2 表示有冲突
      └─▶ = 1 表示无冲突（或广播）
```

**Bank冲突修复示例**：
```cpp
// ❌ Bank冲突：步长为32的列访问
__shared__ float tile[32][32];
// 线程tid访问 tile[tid][col]，同一warp都访问同一个Bank

// ✅ 无冲突：添加1个元素填充
__shared__ float tile[32][33];
// 线程tid访问 tile[tid][col]，不同Bank
```

---

**诊断B2: 检查共享内存使用量**
```
计算每个Block使用的共享内存大小
  │
  ├─▶ > 48KB per Block?
  │   └─▶ 共享内存占用过多，可能影响Block并发数
  │       ├─▶ 减少共享内存使用
  │       ├─▶ 分阶段使用，重用空间
  │       └─▶ 考虑使用动态共享内存
  │
  └─▶ < 16KB per Block?
      └─▶ 共享内存使用较少
          ├─▶ 是否应该使用更多共享内存减少全局访问?
          └─▶ 或者当前内核不适合大量共享内存?
```

---

#### 分支C: 特殊内存类型问题

**诊断C1: 常量内存使用**
```
检查常量内存使用情况
  │
  ├─▶ 只读数据是否使用了 __constant__?
  │   ├─▶ 常量内存有专门的缓存，适合广播访问
  │   └─▶ warp内所有线程访问同一个地址效率最高
  │
  └─▶ 常量内存使用量是否 > 64KB?
      └─▶ 超出限制，编译器会放到全局内存
          └─▶ 考虑分批次，或改用纹理内存
```

---

**诊断C2: 纹理内存使用**
```
检查是否适合使用纹理内存
  │
  ├─▶ 访问模式是否为2D空间局部性?
  │   └─▶ 适合纹理内存（2D缓存优化）
  │
  ├─▶ 是否需要滤波/插值?
  │   └─▶ 纹理硬件支持插值
  │
  └─▶ 是否只读?
      └─▶ 纹理内存只能只读
```

---

### 阶段四：数据传输优化

#### 检查3: 主机端内存优化

```
检查 CPU -> GPU 和 GPU -> CPU 数据传输
  │
  ├─▶ 是否使用了 cudaMallocHost (固定内存)?
  │   ├─▶ 固定内存传输更快
  │   ├─▶ 支持异步传输
  │   └─▶ 缺点：占用物理内存，不能swap
  │
  ├─▶ 传输批次是否太小?
  │   └─▶ 建议批次大小 > 1MB 以获得高效率
  │
  └─▶ 是否可以使用流重叠计算和传输?
      └─▶ 实现流水线，隐藏传输延迟
```

---

### 阶段五：优化验证

```
实施优化措施后
  │
  ├─▶ 带宽是否提升?
  │   ├─▶ 提升 > 20% → 优化有效，继续优化
  │   ├─▶ 提升 < 5% → 优化效果有限，尝试其他方向
  │   └─▶ 性能下降 → 回滚，分析原因
  │
  ├─▶ 现在带宽占理论值的百分比?
  │   ├─▶ > 70% → 带宽利用良好
  │   ├─▶ 50-70% → 还有优化空间
  │   └─▶ < 50% → 需要继续深入分析
  │
  └─▶ 是否引入了新的瓶颈?
      ├─▶ 例如：更多共享内存可能导致低占用率
      ├─▶ 例如：更多寄存器可能导致低占用率
      └─▶ 需要综合权衡
```

## 常见问题快速检查表

| 问题 | 检查项 | 目标值 | 典型优化方案 |
|------|--------|--------|------------|
| 非合并访问 | gld_transactions_per_request | < 2 | 调整索引，AoS→SoA |
| Bank冲突 | shared_efficiency | > 90% | 添加填充，调整步长 |
| L1命中率低 | l1_cache_global_hit_rate | > 50% | 分块，增加局部性 |
| 传输效率低 | 带宽/理论峰值 | > 70% | 使用固定内存，批量传输 |
| 向量访问 | 是否使用float4 | 推荐 | 改用向量类型 |
| 间接访问 | data[indices[idx]] | 尽量避免 | CPU端重排数据 |

## 优化案例

**案例: 图像卷积带宽利用率只有30%**

问题描述：
- 输入：2048×2048 浮点图像
- 核大小：5×5
- 初始带宽只有 ~150 GB/s（理论峰值 500 GB/s）

诊断流程：
1. Nsight Compute 显示 gld_transactions_per_request = 8
2. 查看代码发现：每个线程读取周围25个像素
3. 访问模式不连续，大量非合并

优化方案：
1. 使用共享内存分块（32×32 tile）
2. 每个线程读取tile内连续像素
3. 使用向量加载 float4 一次读4个像素

结果：
- 带宽提升到 ~420 GB/s (84% 理论值)
- 整体性能提升 2.8 倍

---

## 内存优化优先级总结

1. **合并访问**：最重要，先保证所有全局内存访问都是合并的
2. **数据重用**：使用共享内存/L1缓存减少全局内存访问
3. **访问模式**：调整为连续、对齐的访问模式
4. **数据传输**：优化CPU-GPU之间的数据传输
5. **特殊内存**：合理使用常量内存、纹理内存
6. **向量化**：使用向量类型增加每个请求的数据量
