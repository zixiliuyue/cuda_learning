开始
  │
  ├─▶ 步骤1: 确认是否真的慢？
  │       ├─▶ 是 → 继续
  │       └─▶ 否 → 结束
  │
  ├─▶ 步骤2: 整体性能分析
  │       └─▶ 使用 Nsight Systems
  │

## 诊断流程详解

### 阶段一：问题确认

#### 问题1: 与CPU版本对比，加速比是否合理？

```
测量GPU内核时间 vs CPU时间
  │
  ├─▶ 加速比 < 1x?
  │   ├─▶ 可能原因:
  │   │   ├─▶ 数据传输时间太长
  │   │   ├─▶ 问题规模太小（启动开销主导）
  │   │   ├─▶ 内核实现有严重bug
  │   │   └─▶ CPU代码已经高度优化
  │   │
  │   └─▶ 建议措施:
  │       ├─▶ 增大问题规模（至少百万级元素）
  │       ├─▶ 优化数据传输（批量、异步）
  │       └─▶ 检查内核正确性
  │
  └─▶ 加速比 > 1x 但低于预期？
      └─▶ 继续深入诊断
```

**工具**：
- CPU端计时：`std::chrono`
- GPU端计时：`cudaEventRecord`

---

### 阶段二：整体性能分析（使用Nsight Systems）

#### 检查1: GPU利用率

```
查看 "GPU Utilization" 时间线
  │
  ├─▶ GPU利用率 < 50%?
  │   ├─▶ 可能原因:
  │   │   ├─▶ CPU-GPU数据传输瓶颈
  │   │   ├─▶ 内核启动开销
  │   │   ├─▶ 同步等待过多
  │   │   └─▶ 并行度不足（Grid太小）
  │   │
  │   └─▶ 建议措施:
  │       ├─▶ 批量传输，减少传输次数
  │       ├─▶ 使用CUDA流重叠计算和传输
  │       ├─▶ 增大Grid/Block大小
  │       └─▶ 合并小内核
  │
  └─▶ GPU利用率 > 80%?
      └─▶ 说明GPU忙，继续分析内核本身
```

#### 检查2: 数据传输时间占比

```
计算数据传输时间 / 总时间
  │
  ├─▶ 占比 > 50%?
  │   ├─▶ 瓶颈在数据传输
  │   │
  │   └─▶ 建议措施:
  │       ├─▶ 使用固定内存（cudaMallocHost）
  │       ├─▶ 实现流水线重叠
  │       ├─▶ 压缩数据
  │       └─▶ 考虑是否真的需要GPU
  │
  └─▶ 占比 < 20%?
      └─▶ 瓶颈在内核计算，继续深入
```

---

### 阶段三：内核级分析（使用Nsight Compute）

#### 运行 Nsight Compute 分析

```bash
ncu --set full -o kernel_profile ./your_app
```

**重点查看的指标**：
1. 执行时间（Duration）
2. 内存吞吐量（Memory Throughput）
3. SM效率（SM Active / SM Utilization）
4. 分支效率（Branch Efficiency）
5. 占用率（Achieved Occupancy）

---

#### 分支A: 内存瓶颈诊断

```
检查内存相关指标
  │
  ├─▶ DRAM读取吞吐量 > 理论峰值的 70%?
  │   └─▶ 内存带宽饱和，属于"好"的瓶颈
  │       └─▶ 优化方向: 减少内存访问量
  │
  ├─▶ DRAM读取吞吐量在 30-70% 之间?
  │   └─▶ 部分利用，可能有改进空间
  │       ├─▶ 检查合并访问
  │       ├─▶ 检查L2缓存命中率
  │       └─▶ 检查访问模式
  │
  └─▶ DRAM读取吞吐量 < 30%?
      └─▶ 内存严重未充分利用，需要深入诊断
          ├─▶ 诊断A1: 非合并访问检查
          ├─▶ 诊断A2: 共享内存Bank冲突
          └─▶ 诊断A3: 访问模式问题
```

**诊断A1: 非合并访问检查**
```
查看 gld_transactions_per_request
  │
  ├─▶ 值 > 4 → 严重非合并
  │   └─▶ 解决方案:
  │       ├─▶ 检查数组索引模式（idx = block * blockDim + thread）
  │       ├─▶ 结构体数组(AoS)转为数组的结构体(SoA)
  │       └─▶ 调整2D数组访问顺序
  │
  └─▶ 值 < 2 → 合并良好
```

**诊断A2: 共享内存Bank冲突**
```
查看 shared_efficiency
  │
  ├─▶ < 70% → 有Bank冲突
  │   └─▶ 解决方案:
  │       ├─▶ 添加填充（如 shared[32][33]）
  │       ├─▶ 调整访问步长
  │       └─▶ 使用向量类型
  │
  └─▶ > 90% → 共享内存效率良好
```

---

#### 分支B: 计算瓶颈诊断

```
检查计算相关指标
  │
  ├─▶ SM利用率 > 80% 且 内存吞吐量 < 30%?
  │   └─▶ 真正的计算密集型
  │       ├─▶ 检查指令吞吐量
  │       ├─▶ 考虑使用Tensor Core（FP16/BF16）
  │       └─▶ 算法层面优化（减少计算量）
  │
  ├─▶ 分支效率 < 90%?
  │   └─▶ 分支发散问题
  │       ├─▶ 同一warp内线程走不同路径
  │       ├─▶ 优化条件分支
  │       └─▶ 使用分支内建函数
  │
  ├─▶ 指令重放（Instruction Replay）高?
  │   └─▶ 数据相关性问题
  │       ├─▶ 打破依赖链
  │       └─▶ 增加指令级并行
  │
  └─▶ 特殊函数调用频繁?
      └─▶ 内置函数优化
          ├─▶ 使用快速数学库 (-use_fast_math)
          ├─▶ 查表代替计算
          └─▶ 数值近似优化
```

---

#### 分支C: 延迟瓶颈诊断

```
检查延迟隐藏相关指标
  │
  ├─▶ Achieved Occupancy < 30%?
  │   └─▶ 低占用率，无法有效隐藏延迟
  │       ├─▶ 诊断C1: 检查Block大小
  │       ├─▶ 诊断C2: 检查寄存器使用量
  │       └─▶ 诊断C3: 检查共享内存使用量
  │
  ├─▶ 内存访问延迟高但占用率足够?
  │   └─▶ 可能需要增加每个线程的工作量
  │       ├─▶ 每个线程处理更多元素
  │       └─▶ 改进ILP（指令级并行）
  │
  └─▶ 同步开销大?
      └─▶ 同步相关问题
          ├─▶ 减少 __syncthreads() 调用频率
          ├─▶ 避免在分支内同步
          └─▶ 考虑使用 warp 内建原语
```

**诊断C1: Block大小检查**
```
检查Block大小是否合理
  │
  ├─▶ Block大小 < 128?
  │   └─▶ 建议增大到128-512
  │
  ├─▶ Block大小不是32倍数?
  │   └─▶ 调整为32的倍数
  │
  └─▶ Block大小 > 1024?
      └─▶ 考虑是否必要，可能导致低占用率
```

**诊断C2: 寄存器使用检查**
```
查看每个线程的寄存器使用量
  │
  ├─▶ > 64 寄存器/线程?
  │   └─▶ 寄存器压力大
  │       ├─▶ 使用 __launch_bounds__ 限制
  │       ├─▶ 减少活跃变量，重用寄存器
  │       └─▶ 考虑减小Block大小
  │
  └─▶ < 32 寄存器/线程?
      └─▶ 寄存器压力小，占用率低可能是其他原因
```

**诊断C3: 共享内存使用检查**
```
查看每个Block的共享内存使用
  │
  ├─▶ > 32KB/Block?
  │   └─▶ 共享内存压力大
  │       ├─▶ 减少共享内存使用
  │       ├─▶ 分阶段使用，重用共享内存
  │       └─▶ 考虑动态共享内存
  │
  └─▶ < 8KB/Block?
      └─▶ 共享内存压力小，占用率低是其他原因
```

### 阶段四：优化验证

```
实施一项优化措施
  │
  ├─▶ 性能提升 > 10%?
  │   ├─▶ 是 → 记录收益，继续优化
  │   └─▶ 否 → 回滚，尝试其他优化方向
  │
  ├─▶ 性能反而下降?
  │   └─▶ 分析原因
  │       ├─▶ 优化过度？
  │       ├─▶ 引入了新的瓶颈？
  │       └─▶ 正确性问题？
  │
  └─▶ 性能达到预期?
      ├─▶ 是 → 结束诊断
      └─▶ 否 → 回到阶段二，继续分析
```

**重要原则**：
- 每次只改一项
- 改动前后都要测量
- 记录每次优化的性能变化

## 常见问题快速检查表

| 问题 | 检查项 | 指标阈值 | 解决方案 |
|------|--------|---------|---------|
| 非合并访问 | gld_transactions_per_request | < 2 最佳，> 4 需优化 | 调整索引模式，AoS→SoA |
| Bank冲突 | shared_efficiency | > 90% 最佳，< 70% 需优化 | 添加填充，调整步长 |
| 分支发散 | branch_efficiency | > 95% 最佳，< 80% 需优化 | 调整条件，优化分支 |
| 低占用率 | achieved_occupancy | > 50% 良好，< 30% 需优化 | 调整Block大小，减少寄存器 |
| 寄存器溢出 | spill stores/loads | 应该为0 | 减少寄存器使用，调整launch bounds |
| 同步过多 | 查看源代码 | 按需同步 | 减少不必要的 __syncthreads() |

## 诊断案例

**案例: 矩阵乘法性能只有理论值的30%**

诊断流程：
1. Nsight Systems 查看 → GPU利用率95%，说明不是传输问题
2. Nsight Compute 分析 → DRAM吞吐量只有40%
3. 查看全局内存加载效率 → gld_transactions_per_request = 8
4. 结论：严重的非合并访问

解决方案：
- 检查发现访问模式是 `A[row * lda + col]`
- 添加分块（tiling）优化，使用共享内存
- 结果：性能提升3倍，达到理论值的90%

---

## 总结：优化优先级顺序

1. **正确性优先**：确保结果正确，不要为了性能牺牲正确性
2. **算法优化**：O(N²) → O(N log N) 的提升远大于任何底层优化
3. **内存访问**：优化合并访问、减少全局内存访问
4. **并行粒度**：确保足够的并行度，合理的Block/Grid大小
5. **指令级优化**：最后才考虑ILP、特殊指令等
